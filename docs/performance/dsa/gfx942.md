# dsa — DeepseekSparseAttn sparse-MLA forward (AMD gfx942, MI300A)

Latency + roofline characterization of the DSA sparse-MLA forward in
`src/c/vkernels/kernels/dsa.{cpp,hip}` (issue #51) — the second stage of
the GLM-5.3-Flash / DeepSeek-V3 sparse attention: an external indexer has
already picked, per query token, the top-`topk` KV entries (`indices`);
this kernel scores each query against exactly those keys and produces the
combined attention output:

$$\text{out}[i,h] = \sum_k 2^{\,\text{sm\_scale}\cdot q_{i,h}\cdot k_{\text{idx}_k} - \text{lse}_{i,h}} \; v_{\text{idx}_k}\qquad(\text{masked } \text{idx}_k \to w=0)$$

with `W = dim + tail_dim` (`tail_dim == 0` for GLM-5.3-Flash — the shape
tilelang cannot compile — and `tail_dim = 64` for DeepSeek-V3). Replaces
the tilelang `sparse_mla_fwd_decode_partial` (+`_combine`) decode kernels
and the `_v1`/`_v2` prefill kernels, which GPU-fault on gfx942, so there
is **no tilelang baseline delta measurable on this hardware**.

**Implementation under test** (see [`docs/kernels/dsa.md`](../../kernels/dsa.md)):
CPU fp32 two-pass oracle (`dsa_sparse_fwd_cpu`, always compiled) + HIP
online-softmax kernel — one block per `(BQ query rows, head)` pair,
streaming its `topk` selected keys one at a time in `block_I` tiles,
fp32 accumulation with bf16 storage, grid `(ceil(S_q/BQ), H)`; the bench
also sweeps `BQ` through `dsa_sparse_fwd_with_tile` (small autotuner).
For decode there is additionally the **split-key path**
(`dsa_sparse_fwd_split`): the `topk` index range is divided across
`split_kv` partial blocks (grid `(ceil(S_q/BQ), H, split_kv)`, each
writing its normalized fp32 partial output + per-split lse) and a
combine kernel merges the splits in the log2 domain — the same
partial+combine scheme as FlyDSL's `mla_fwd_decode` and the tilelang
`decode_partial`/`_combine` pair.

## Correctness (on the bench node)

Device-vs-oracle **17/17 PASS** — the 11 rows below (GLM-5.3-Flash
`tail_dim == 0` decode / short / prefill, DeepSeek-V3 `tail_dim > 0`,
plus two tiny hand-checked shapes) plus **6 split-path rows**
(`dsa_sparse_fwd_split` at split=1 (degenerate delegation), 2 (the
`dsa_sparse_fwd_split_for` value), 7 (uneven — chunk boundaries land
mid-tile), 14 (DSv3 decode), 3 (full-topk decode), and 128 (one key per
split); the log2-domain merge is exact, so tolerances are unchanged).
`out` max_rel ≤ 3.9e-3 against a 2e-2 bf16 tolerance, LSE exact to
fp32. One harness fix was needed first (see Caveats): the tiny
`topk=2` hand-check shapes predated the issue-#59 launch-precondition
enforcement and aborted (`topk % (block_I*inner_iter)` with
`block_I=64`); they now pass `block_I = topk` (grouping is
result-independent).

## Workload

GLM-5.3-Flash (`dim=256, tail_dim=0 → W=256, d_v=256, H=64`) and
DeepSeek-V3 (`dim=576, tail_dim=64 → W=640, d_v=512, H=16`) shapes;
`S_q` sweeps decode → prefill, `topk` the indexer fan-out. Roof:
1307 TFLOP/s bf16, 5300 GB/s HBM3, ridge ≈ 247 FLOP/B.

## Split-key decode (`dsa_sparse_fwd_split`) — the occupancy fix, 20.0x at full topk

The plain decode grid is `(ceil(S_q/BQ), H)` — **64 blocks on 228 CUs**
at the GLM-5.3-Flash shape — so decode is bound by each block's SERIAL
key chain (~1.2 us per key: a load→use dependency, no pipelining
across keys), not by any roof. `dsa_sparse_fwd_split` divides the
`topk` index range across `split_kv` partial blocks + a combine pass
(grouping-independent; the merge is the exact log2-domain softmax
merge, correctness rows above). The sweep (same node, same run):

| topk | split=1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 | 256 | best |
|-----:|--------:|----:|----:|----:|----:|----:|----:|-----:|-----:|------|
| 2048 | 3119.5 | 1602.2 | 823.9 | 431.0 | 241.8 | 163.0 | **156.3** | 236.3 | 397.2 | 64 → **20.0x**, 430 GB/s |
| 256 | 396.8 | 212.7 | 116.5 | 73.0 | **58.9** | 68.3 | 104.1 | 184.5 | 349.0 | 16 → **6.7x**, 144 GB/s |
| 128 | 202.9 | 112.9 | 66.8 | 48.6 | **45.4** | 60.6 | 99.0 | 182.5 | — | 16 → **4.5x**, 94 GB/s |
| 256 (DSv3, H=16) | 741.3 | 387.4 | 207.3 | 122.1 | **94.2** | 105.6 | 162.4 | 293.8 | 565.6 | 16 → **7.9x**, 56 GB/s |

(us(med), H=64 dim=256 except the DSv3 row; full table in the raw log
section 3.) Two findings shaped the shipped recommendation
(`dsa_sparse_fwd_split_for`):

  * **The optimum is NOT CU-filling.** The indexer's floor formula
    (`num_cu / blocks`, 3–4 at H=64) is 5–6x off; the best split
    over-subscribes the machine up to ~18 waves because what matters is
    shortening each block's serial chain, not filling CUs. The measured
    optimum sits at 8–32 keys per split on every decode shape, and
    `ceil(sqrt(2*topk))` lands on the best or its nearest neighbor on
    all four (2048→64 = the best; 256→23; 128→16 = the best).
  * **Prefill must NOT split**: at S_q=8192 the plain grid already runs
    at 21–28% of the HBM roof, and `split_for` returns 1 there
    (`blocks >= num_cu` term).

Serving takeaway after the fix (per layer, GLM-5.3-Flash decode,
`split_for` recommendation): **0.045 ms** (topk=128) / **0.059 ms**
(topk=256) / **0.156 ms** (full topk=2048) — the forward no longer
dominates the indexer stage (0.2–0.9 ms); the topk-linear decode
penalty is gone.

## The decode binding constraint is OCCUPANCY / key-stream latency, not HBM

  * **Decode grids are tiny**: the launcher is `grid(ceil(S_q/BQ), H)` —
    the GLM-5.3-Flash decode shape runs **64 blocks on 228 CUs** (one
    per head), DSv3 decode **16 blocks**. Each block streams its `topk`
    keys strictly serially (one key per lane iteration, no double-buffered
    key tile), so per-block latency ≈ `topk` serial L2 round-trips.
  * **Effective bandwidth confirms it**: 21.5 GB/s at the full-topk
    decode shape is 0.4% of the HBM roof — but the entire kv working set
    (`topk·W·2 B` = 1 MB at topk=2048) is L2-resident, and the measured
    rate is ~0.3% of MI300A's L2 bandwidth too. The kernel is bound by
    in-flight memory parallelism, not by any roof.
  * **Serving takeaway**: per layer, GLM-5.3-Flash decode paid 0.20 ms
    (topk=128) / 0.40 ms (topk=256) / 3.12 ms (full topk=2048) for the
    sparse forward vs 0.2–0.9 ms for the indexer stage (see
    [`../dsa-topk/gfx942.md`](../dsa-topk/gfx942.md)) — the forward
    dominated and scaled linearly with `topk`. The split-key path below
    removes this: 0.045 / 0.059 / 0.156 ms at the `split_for`
    recommendation, so the indexer is now the slower stage at full
    topk.
  * **Prefill is closer to the roof** (21–28% of HBM at S_q=8192): more
    query blocks hide the key-stream latency; AI 1.8–2.0 FLOP/B is
    ~125× below the ridge, so this kernel family is memory-shaped by
    construction (each selected key is used once per head — the
    H-fold kv re-read is the structural cost the tiled-key/persistent
    follow-on must amortize).
  * **The follow-on levers**, in expected impact order: (1) ~~split_kv for
    the forward~~ **DONE** — `dsa_sparse_fwd_split` + `split_for`, 20.0x
    at full topk (section above); (2) double-buffered key tiles to
    overlap loads with the online-softmax update (now the top lever:
    8–32 keys/split × ~1.2 us serial chain is the remaining latency);
    (3) an MFMA path for the Q·K dot (the indexer's mfma variant is the
    fastest there); (4) batched-decode rows — serving decode is
    S_q=batch (8–64), where the plain grid amortizes on its own (the
    split sweep only covers S_q=1; the S_q=64 short shape runs 157
    GB/s unsplit).

## FlyDSL (rocm/flydsl) — probe result: runs on gfx942, D=256 wrong, ours ~2.7x/byte faster

FlyDSL (ROCm's python-kernel DSL, the repo that now carries the
MLA/flash kernels tilelang could not compile) was probed on the same
node as a candidate missing-baseline source. Setup: `pip install
flydsl` (wheel 0.3.2, python3.11) + `torch 2.9.1+rocm6.3` + a repo
checkout for the `kernels/` package; the wheel's MLIR runtime links
`libamdhip64.so.7`, absent on this ROCm 6.3 node, so a compat symlink
(`libamdhip64.so.7 -> /opt/rocm-6.3.0/lib/libamdhip64.so.6`) is needed
(kernels launch and compute through it; a few benign
`hipErrorIllegalState` messages appear at warmup).

`flydsl_flash_attn_func` (gfx942 generic route, dense bf16) at the
GLM-5.3-Flash decode memory pattern (Sq=1, Skv=2048, H=64 — one q row
per head streaming all keys, structurally identical traffic to our
sparse forward at topk=2048 minus the gather):

| shape (dense) | med us | bytes | GB/s | output vs fp32 reference |
|---|---:|---:|---:|---|
| H=64, D=128, Skv=2048 | 208 | 67 MB | 322 | **correct** (maxrel 0.005) |
| H=64, D=256, Skv=2048 | 218 | 134 MB | 615 | **WRONG** (maxrel 27) |
| H=8, D=256, Skv=2048 / H=16, D=256 / H=64, D=256, Skv=512 | ~ | ~ | ~ | **WRONG** (maxrel 11–30) — D=256 breaks regardless of H, Skv |
| H=64, D=576 (DSv3) | — | — | — | launch-time assertion (unsupported) |
| tiny (Sq=128, Skv=128, H=8, D=64) | 213 | — | — | correct; ~200 us DSL-runtime floor on small shapes |

Findings:

  * **Not usable as the DSA baseline.** It is dense-only (no topk-gather
    sparse kernel ships), and its gfx942 generic path is numerically
    broken at `head_dim == 256` — exactly GLM-5.3-Flash's shape — while
    D=128 verifies to bf16 tolerance. (Upstream bug, D=256-conditional,
    independent of H/Skv; worth filing.)
  * **But the perf signal validates the split-key work.** FlyDSL's
    compiler-tuned dense decode moves 67 MB in 208 us (322 GB/s); our
    split sparse kernel moves 134 MB (2x the bytes, D=256 + gather) in
    156 us (~860 GB/s true; the table's 430 GB/s uses the repo byte
    convention that counts the kv term once — see note). Same node, same
    pattern: **~2.7x more bandwidth per byte** than FlyDSL's flash
    codegen at the shapes that matter. Pre-split (3.12 ms), FlyDSL would
    have beaten our kernel by 14x — the gap was exactly the one the
    split path closed.
  * **Byte-model note (this doc).** The `GB/s` column above and in the
    tables counts kv bytes once per head per read-pass (repo-wide
    convention inherited from the original roofline script); FlyDSL's
    probe model counts K and V separately. The 430-vs-860 GB/s
    difference is bookkeeping, not physics — latency comparisons are
    model-free.
  * Remaining use: an authoring stack for future kernels (encodes the
    MFMA fragment layout at a higher level than our hand-written
    `gemm_bf16.hip`, autotunes, and its `mla_fwd_decode` fp8/MFMA
    decode-kernel design targets gfx950 MFMA — a candidate for the
    gfx950 port) — gated on the D=256 bug and the ROCm-7 wheel
    dependency being fixed.

## Caveats and notes

  * **Clocks.** `rocm-smi --setperflevel high` is not permitted on this
    cluster; idle sclk was 95–96 MHz. Variance-driven iteration (median
    over ≥ 20 reps, CV < 3%) keeps the reported medians stable, but
    absolute µs are upper bounds; the roofline ratios and the topk/BQ
    scalings are the robust signals.
  * **Timing methodology.** `hipEventElapsedTime` around single launches;
    sub-µs rows print `<res` (below event resolution). All rows here are
    well above resolution except none — every dsa row is ≥ 200 µs.
  * **Event 0.0 quirk (fixed this run).** With rapid-fire event pairs
    around DVFS clock transitions, ROCm 6.3 occasionally reports an
    elapsed of exactly 0.0 even though the kernels ran (verified by
    output checksum on the affected configs) — this produced `0.0 us /
    inf GB/s` rows in the first split sweep at flaky positions
    (topk=256/split=16, then topk=128/splits 8+16 on the re-run). All
    six bench harnesses now discard non-positive samples
    (`bench_us`/`measure_once`); the stored log is from the fixed
    harness and has no such rows.
  * **Login-node gotcha (probe debugging).** HIP launches on the beverin
    login nodes silently no-op (no gfx942 agent): hipMalloc/memcpy
    succeed, `hipGetLastError` stays clean, outputs stay zeroed, and
    event pairs read ~4 µs. Any standalone probe must run under
    `srun --partition=mi300` — the script does, ad-hoc ssh one-liners
    must too.
  * **Tiny-shape harness fix (this run).** `test_dsa_correct.hip`'s two
    `topk=2` hand-check shapes predated the issue-#59 precondition
    enforcement (`topk % (block_I·inner_iter) == 0`) and aborted the
    whole binary with an uncaught `std::invalid_argument` — on main,
    since #59, the device gate has been unrunnable as written. Fixed by
    giving the tiny cases `block_I = topk` (tiling does not change the
    result); the nine service shapes are untouched.
  * **Same-build indexer numbers** are included in the raw log (section
    5): they match [`../dsa-topk/gfx942.md`](../dsa-topk/gfx942.md)
    within noise (mfma variant fastest, split_kv 4.7× at bs=1).
  * The WIP tree benchmarked here also carries the in-flight `fits_lds`
    cap-parameterization + wmma admission work (GB10 CUDA port); none of
    it touches the gfx942 forward path measured above.

## Journal

Benchmarked the issue-#51 DSA sparse-MLA forward on CSCS beverin
(nid002664, MI300A) — the last GLM-5.3-Flash kernel group without perf
numbers. One blocker surfaced immediately: the device correctness gate
aborted on the tiny hand-check shapes because issue #59's precondition
enforcement (`topk % (block_I·inner_iter) == 0`) landed after the test
was written — a pre-existing main breakage, fixed by passing
`block_I = topk` for those two rows (the grouping is
result-independent). With the gate green (11/11), the benchmark exposes
a clear story: prefill runs at 21–28% of the HBM roof, but decode is
occupancy-bound — 64 blocks on 228 CUs streaming `topk` keys serially —
0.4% of the HBM roof and ~0.3% of L2 bandwidth, scaling linearly with
topk (0.20/0.40/3.12 ms at topk=128/256/2048 per layer). The BQ
autotuner confirms tiles are not the issue (< 6% spread). The highest-
leverage follow-on is split_kv for the forward (the indexer already
proved 4.7× from exactly that), then double-buffered key tiles and an
MFMA dot. The full stack now has measured numbers: indexer → kpool →
sparse fwd, plus MHC pre/post (see [`../mhc/gfx942.md`](../mhc/gfx942.md)).

Follow-up run (same node class, nid002424): implemented the split-key
decode — `dsa_sparse_fwd_split` (partial kernel writing normalized fp32
partials + per-split lse over a contiguous topk chunk, then a
log2-domain combine) with the recommendation helper
`dsa_sparse_fwd_split_for` and a split sweep in `bench_dsa.hip`. First
merge attempt was WRONG in an instructive way: weighting the
UNNORMALIZED per-split numerators by 2^(lse_s − m) — the lse came out
exact while outputs were off by 1.1–11x, because the correct weight
applies to the NORMALIZED per-split output (num/row_sum); one-line fix,
now 17/17 vs the oracle including uneven splits. The sweep killed two
assumptions: (1) the CU-filling split formula is 5–6x off at H=64 (best
is 64 at topk=2048, over-subscribing ~18 waves — the binding constraint
is the per-block serial key chain, so `split_for` now recommends
ceil(sqrt(2·topk)), which lands on the measured best on all four
shapes); (2) the bench's event-timing harness can emit exact-0.0 samples
under DVFS transitions — all harnesses now discard them (the flaky
`0.0 us / inf` rows were verified against output checksums before
blaming the kernel). Net: full-topk decode 3.12 → 0.156 ms per layer
(20.0x, 430 GB/s), topk=256 0.40 → 0.059 ms (6.7x), topk=128 0.20 →
0.045 ms (4.5x), DSv3 decode 0.74 → 0.094 ms (7.9x) — the forward no
longer dominates the indexer at any serving shape. Also surveyed
ROCm/FlyDSL for the perf doc's baseline gap and then PROBED it on-node:
it installs on beverin (wheel 0.3.2 + torch 2.9.1+rocm6.3 + a
libamdhip64.so.7 compat shim), its gfx942 dense flash verifies at
D=128 but is numerically WRONG at D=256 (maxrel 27 — the GLM-5.3-Flash
shape, upstream-bug-shaped) and unsupported at D=576, so it cannot
serve as the DSA baseline; at the D=128 decode pattern it moves bytes
at 322 GB/s vs our split kernel's ~860 GB/s true (~2.7x/byte for us).
Recorded in the FlyDSL section above with reproduce steps.
