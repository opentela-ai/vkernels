# moe-fused — MXFP4 fused-MoE grouped GEMM (AMD gfx942, MI300A)

An end-to-end Mixture-of-Experts layer that wires vkernels' four low-level
MXFP4 primitives into the xkernels `fused_moe_mxfp4` interface: fp4→bf16
dequantization, the gate+up grouped GEMM, SwiGLU activation, and the down
grouped GEMM with a routed scatter-add combine — fused into **two kernel
launches** (plus a tiny routing-weight gather). Weights stay in packed
MXFP4 E2M1 (2 values/byte) with ue8m0 per-group scales; no full bf16
materialization of the ~138 GB expert weight buffer.

Two tile configs are compiled in, selected by `block_size` (16 = decode,
64 = prefill). The decode config targets small-batch autoregressive decode
(BM=16, BN=64, 64 threads); the prefill config targets prompt processing
(BM=64, BN=64, 256 threads) and reuses each dequantized B tile across 64
rows instead of 16.

## Kernel (pseudocode)

```cpp
// Stage 0 — gate_up + SwiGLU (one bf16 rounding, matches xkernels oracle)
//   act[EM, ispp] = silu(clamp(A_sorted @ w13_gate + b_gate, L))
//                 · clamp(A_sorted @ w13_up   + b_up,   L)
// Stage 1 — down + routed combine (caller zero-initialises out)
//   out[M, hidden] += act @ w2^T · topk_w_sorted + b2     (atomicAdd per token)
//
// Dequant is inline in the K-loop; MFMA via the clang builtin
// __builtin_amdgcn_mfma_f32_16x16x16bf16_1k (16x16x16 tiles, K=64 per loop).
// Decode:   grid=(EM/16, N/64, 4), 64 threads; blockIdx.z splits N into 4×16.
// Prefill:  grid=(EM/64, N/64),  256 threads (4 wavefronts × 4 col fragments).
```

Full source: `src/c/vkernels/kernels/moe_fused{.hpp,.cpp,.hip}`,
`moe_device.hip` (E2M1/ue8m0 decode, bf16 rounding). The correctness oracle
is `fused_moe_mxfp4_cpu` (block-for-block mirror of the GPU path).

## What was implemented

- **Two fused kernels** (`gateup_swiglu_kernel[_prefill]`,
  `down_combine_kernel[_prefill]`): gate and up accumulate in fp32 in the
  same kernel and the SwiGLU product is rounded to bf16 once, matching the
  xkernels 2-stage oracle exactly (a split 3-kernel pipeline introduced a
  spurious intermediate bf16 rounding). SwiGLU gate is clamped to `L`
  *before* the sigmoid; up is clamped symmetrically to ±L.
- **Inline MXFP4 dequant**: E2M1 nibble → fp32 (LUT in `__constant__`),
  × ue8m0 scale (`s<<23` bit trick), → bf16, written straight to LDS. The
  gate and up weights share one LDS buffer in the prefill kernel (dequant
  gate → MFMA → dequant up → MFMA) to cap LDS at 16 KB.
- **Flat-index `sorted_ids`**: `moe_align_block_size` stores
  `token*top_k + sel` (padded with `M*top_k`), so the routing-weight gather
  keeps the selection index for `top_k > 1`; `act_scratch` is indexed by
  sorted row (not token), so a token routed to multiple experts never races.
- **MFMA fragment layout** (verified empirically with one-hot matrices):
  A `m=lane%16`, B `n=lane%16`, C `col=lane%16, row=(lane/16)*4+i`
  (4 consecutive rows × 1 column per lane).
- **Prefill tile config**: BM=64/BN=64/BK=64, 256 threads, 4 column
  fragments per wavefront. Added in a follow-up for the M>32 regime; the
  BN was later narrowed 128→64 to lift occupancy (see Caveats).
- **Double-buffering experiment** (documented in Caveats): 2-stage LDS was
  implemented, measured, and **reverted** — it halved decode occupancy and
  cost ~50%.

## Caveats and notes

- **Full package, one GCD.** MI300A is a single APU GCD, so every number
  above is the whole device (~1307 TFLOP/s bf16). gfx942's dual-issue
  matrix cores give ~2.5× the gfx90a per-GCD throughput on the same kernel.
- **Occupancy-bound, not barrier-bound.** LDS double-buffering (2-stage
  sA/sB) was implemented and reverted: it doubled decode LDS 6→12 KB,
  halving blocks/CU, and slowed decode ~50% on gfx90a. The redundant barrier
  between the A-tile load and the weight dequant was removed (they write
  different LDS buffers) — a free, small win. Acting on this, the prefill BN
  was narrowed 128→64 (24→16 KB LDS, 64→32 accumulator VGPRs), lifting
  occupancy 2→3 blocks/CU and measuring ~1.3–1.8× faster on gfx942 (M=2048:
  2.58→1.98 ms). The lever is *more* occupancy, not deeper pipelining.
- **~1.5% of peak, and it's the dequant, not the MFMA.** Each block
  dequantizes every fp4 weight inline (LUT + scale + bf16 convert), which is
  ALU-heavy relative to the 16×16×16 MFMAs it feeds. Materializing weights
  once (xkernels Triton's approach) trades 138 GB of HBM traffic for this
  ALU; the fused kernel wins by never touching that buffer.
- **Decode padding waste.** `moe_align_block_size` pads every routed expert
  to a 16-row block, so small-M latency is ~(experts routed)·16 rows, not
  M tokens. A padding-aware launch (skip empty block tails) would help M<32.
- **MI300A decode timing is noisy across nodes.** The APU clock throttles
  with sustained load, so decode M=2048 has been seen anywhere from 3.6 to
  5.0 ms on different `mi300` nodes. The prefill-vs-decode speedups above are
  measured within a single run (same node, same clock state) and are the
  trustworthy comparison; absolute latencies carry ~±30% across nodes.
- **Baseline is torch, not Triton.** xkernels' Triton backend segfaults
  under ROCm 6.2.4 on both gfx90a and gfx942 (SIGSEGV inside Triton 3.3.1),
  so the comparison is against the reference torch loop.
- **SLURM note.** The container image is not shared across compute nodes:
  each `mi300` job must `podman load` it into a fresh `--root/--runroot`
  (in `/tmp`, not the stale `/dev/shm` default), then mount
  `/users/xyao/vkernels-prefill` at `/workspace/vkernels`.

## CPU oracle — host validation surface (issue #41)

Acceptance criterion #1 requires the gfx942 kernel to be "validated against
the CPU oracle at K3 shapes (E=256, hidden=7168, ispp=33792, top_k=16)."
The HIP bench carries a `--no-cpu` flag that skips that check for exactly
the reason called out above ("~1.5% of peak, and it's the dequant" and
"Decode padding waste"): at K3 *decode* (M=1, top_k=16) `moe_align_block_size`
pads each routed expert to a 16-row block, so EM=256 rows hold only 16 real
rows — **93.8% of the oracle's GEMM is over padding rows whose A tile is
zero and which contribute exactly zero.** The CPU reference therefore spends
most of its time on provably-zero work, which is what made the per-call check
impractical to run inside a sweep.

Two bit-exact optimizations to the CPU reference (`src/c/vkernels/kernels/moe_fused.cpp`)
make K3-routing validation feasible on the host:

1. **Padding-skip GEMM.** `moe_gateup_cpu`/`moe_down_cpu` now `continue` past
   rows with `sorted_ids[...] >= N` in the gate/up/down dot-product loops.
   Padding rows already hold the zeroed-tile result (the accumulator is
   zeroed per N-block), so skipping their dot products changes zero output
   bits.  At M=1 this removes ~15/16 of the GEMM.
2. **LUT dequant + per-group scale hoist.** `dequant_weight_tile` reads the
   16-entry fp4-nibble decode and the 256-entry ue8m0 scale from tables
   built once from `fp4nib_to_f32bits_local`/`ue8m0_to_float` (bit-identical
   by construction) instead of re-running the branchy decode twice per
   packed byte, and hoists the per-group ue8m0 scale (shared across
   `group_size` K elements) out of the per-byte loop.  The original loop is
   kept as the golden `dequant_weight_tile_ref`.

**Verification.** A new host-only bench, `meta/benchmarks/bench_moe_fused_oracle.cpp`
(the always-runnable analog of `bench_rccl.cpp`/`bench_pipeline_boundary.cpp`,
no GPU/ROCm), times the reference at the K3 decode routing shape.  Same
`-O3` build, M=1 / top_k=16 / E=256 (93.8% padding):

| shape (M hidden ispp) | before µs | after µs | speedup |
|-----------------------|----------:|---------:|--------:|
| 1  512  1024          |   303 305 |   66 414 |  4.57×  |
| 2  512  1024          |   606 548 |  151 633 |  4.00×  |
| 4  512  1024          |   969 772 |  261 280 |  3.71×  |
| 1  7168  128          |   461 764 |  125 599 |  3.68×  |

The speedup shrinks as M grows (92.7% at M=4, 90.4% at M=8) — exactly the
expected shape of a padding-skip win.

Bit-exactness is asserted, not assumed: `tests/kernels/moe/test_moe_fused.cpp`
adds `Fp4DequantLUTBitExact` (every one of the 256×256 packed-byte × ue8m0-
scale pairs via `memcmp`) and `Fp4DequantLUTHoistVaryingScale` (300 random
tiles with scale varying across the two K-groups, exercising the hoist).
`K3RoutingTopK16` runs the full oracle at E=256 / top_k=16 / M=1 and checks
both the act map (real rows = `SwiGLU(hidden)`, padding rows = 0) and the
combined output (`top_k · act · ispp`) against analytically-known values —
so the GPU kernel has a correct, fast reference to match at the K3 routing
shape the issue names.

**Scope.** Full-K3 hidden/ispp (7168 × 33792) validation stays host-memory-
bound (~6 TB of expert weights cannot be held on a normal host); the
realistic surface is K3 *routing* (top_k=16, E=256, M=1) at a moderate
hidden/ispp where the weights fit.  The routing, block alignment and
`top_k=16` combine paths are identical at either scale — this is the part
the bench and the new tests cover, and the part the GPU-side work
(items 1–5) actually changes.

1. **`int` buffer-size overflow in `bench_moe_fused.hip` (fixed).**  The
   bench computed `w13_sz = E*2*ispp*(hidden/2)` etc. in `int`; at K3 shapes
   this exceeds `INT_MAX` (e.g. 61.9 GB), wraps negative, and as `size_t`
   threw `std::length_error` (real weights) or a spurious

   fit" note was partly this artifact.  Fixed by computing the four `_sz`
   constants in `size_t` (`static_cast<std::size_t>(E) * ...`), mirroring the
   casts in the CPU oracle / tests.  After the fix, ispp=1024 and 2048 run
   cleanly; the K3 *routing* latency-vs-ispp (per-GPU-relevant shape) is:

   | ispp | M=1 µs | M=2 µs | M=4 µs | M=8 µs |
   |-----:|-------:|-------:|-------:|-------:|
   |  512 |   825  |  1058  |  1697  |   —    | (CPU oracle: all ok)
   | 1024 |  1289  |  1896  |  3659  |  7389  |
   | 2048 |  2249  |  3980  |  7916  |   —    |

   (`--kmajor`, gfx942; full numbers in
   `docs/performance/moe-fused/beverin-k3-scaling.txt`.)  The default harness
   (E=256 h4096 i512 k6, swiglu) measures M=1 = 398 µs — matching the
   issue's "~0.45 ms" baseline for acceptance criterion #2.

2. **GPU memory-access fault at ispp ≥ 4096 (and at full K3 ispp=33792, any

   resident (E=32, the per-GPU TP=8 shard), the kernel faults: `Memory

   ispp.  This is a pre-existing kernel limitation, **not** the oracle work,
   and is worth investigating separately: the issue reports K3 serving
   *works* (6/6 factual probes), so the vLLM invocation likely differs from
   this single-GPU bench shape (tile sizes, the act/weight strides, or a
   different kernel variant).  Until that is reconciled, the bench cannot
   produce the full-K3 (ispp=33792) single-decode latency; the
   moderate-ispp routing numbers above and the default-harness 398 µs are
   the validated per-GPU baselines for acceptance criterion #2
   (~0.45 ms → ≤ 0.30 ms).  Item 5 (wavefront-specialised dequant) is the
   remaining GPU lever toward that target.

## Journal

**What was done.** Validated the fused MoE (decode + prefill) and the four
primitives on MI300A (gfx942) after the gfx90a bring-up, and recorded the
results under `docs/performance/`. Prefill correctness passes at
`max_rel < 0.02`, decode at `max_rel < 0.00001`.

**Challenges.**
1. *Cross-node image loading.* SLURM jobs land on different MI300A nodes,
   none of which share the login node's podman storage. The working recipe
   is a fresh per-job `podman --root $PR/root --runroot $PR/run load` into
   `/tmp` (the default `/dev/shm` root carries a stale boot-ID after node
   reboots and fails with exit 125).
2. *Triton baseline unavailable.* xkernels' Triton backend SIGSEGVs under
   ROCm 6.2.4 + Triton 3.3.1 on both architectures, so the baseline is the
   torch loop (which gfx942 also accelerates ~1.3× over gfx90a).
3. *Occupancy was the real lever.* Narrowing the prefill BN 128→64 (24→16 KB
   LDS, 64→32 accumulator VGPRs) lifted occupancy 2→3 blocks/CU and won
   ~1.3–1.8× on gfx942, consistent with the ~1.5× measured cleanly on gfx90a.

**Future work.**
- Raise occupancy further: a BM=32 prefill tile (or `__launch_bounds__`
  nudging) could cut VGPRs below 64 and reach 4 blocks/CU; split gate/up to
  reduce live registers is another path.
- **Wavefront-specialised producer/consumer dequant once occupancy
  saturates — DONE and REJECTED (issue #76).**  See *Issue #76 — prefill
  variants* below: using the N tile to add grid parallelism is what wins;
  the producer/consumer split is correct but slower, because the dequant
  ALU demand is ~30× the MFMA issue demand (measured off the gfx942 ISA:
  see *Why variant 3 lost* below).
- Revisit the Triton baseline when ROCm 6.3 / a fixed Triton ships.

## Issue #76 — prefill variants (MI300A / gfx942)

**Context.**  Issue #76 reports vLLM prefill at 1.98 ms / ~26 TFLOP/s for
this MoE and asks for ≥ 1.5× on prefill with no decode regression, plus
explicitly proposes a producer/consumer wavefront split as the mechanism.

**What was actually limiting the kernel.**  The prefill gateup kernel at
(E=8, hidden=4096, ispp=512, M=2048) launches only
`(EM/64) × (ispp/64) = 64 × 8 = 512` blocks over 304 CUs — only ~1.7
workgroups per CU of total work, and the 107-VGPR baseline admits just 2
resident blocks/CU (~2 wavefronts per SIMD).  It is **latency-bound, not
throughput-bound**: the SIMDs sit idle waiting for the serialised
`load A → sync → dequant → sync → MFMA` chain.  Weight-dequant
work is independent of the N tile, but grid size is proportional to
`ispp / kBN`, so narrowing the tile buys concurrency (and drops the live
accumulator footprint from 32 to 4 VGPRs at kBN=16).  The N tile's one
non-amortising cost is the A tile, which every n-block of an m-block
re-reads: A traffic scales as `1/kBN` (~256 MB → ~1 GB at M=2048), which is
exactly why the narrow tile gives back ~1.4% at the largest M.

**The resource picture that follows from that.**  Compiled with ROCm 6.3.0
`--offload-arch=gfx942`, one block = 256 threads = 4 wavefronts:

| kernel | kBN | VGPR | LDS | blocks/CU (VGPR / LDS) | resident warps/SIMD | grid at M=2048 | workgroups/CU |
|---|---:|---:|---:|---|---:|---:|---:|
| `gateup_swiglu_kernel_prefill` (v0) | 64 | 107 | 16.25 KB | 2 / 3 | 2.0 | 512 | 1.7 |

**Why variant 3 lost.**  The split is correct and does overlap dequant with
MFMA, but it cannot shorten the critical resource.  Per K-block the kernel
issues 16 MFMA warp-instructions and the dequant that must feed them costs
*31× that*, counted statically off the gfx942 ISA (ROCm 6.3.0 clang-18):

| kernel (`gateup`, one kb loop body) | VALU warp-inst | MFMA warp-inst | ratio |
|---|---:|---:|---:|
| `_prefill_pipe<16>` (shipped, v5) | 249 | 8 | 31.1× |
| `_prefill_pipe<32>` (v2) | 457 | 16 | 28.6× |
| `_prefill_ws<32>` (v3, specialised) | 511 | 16 | 31.9× |

The fp4→bf16 decode is ~4 lane-ALU ops per fp4 element on gfx942, and it
dominates every path the block can take.  Handing the dequant to four
*other* warps does not remove it from the four SIMDs — it parks the four
MFMA warps while the four producer warps issue the same ALU, and the
result is 1815 µs vs 1140 µs for the plain pipelined variant 2.  The gate
is the dequant ALU, not the MFMA/LDS serialisation.  A hardware fp4→bf16
convert would move that gate; ROCm 6.3/6.4 expose neither `v_cvt_scalef32*`
nor `v_mfma_scale*` for gfx942 (checked against the shipped clang-18
builtin tables), so the dequant stays hand-written for now.  Variant 3 is
kept in the tree behind the flag as the evidence for that conclusion.

**Caveat.**  The 32-wide gateup tile (v2, 1140 µs) is ~1.4% faster than the
16-wide default (v5, 1159 µs) at M=2048 and much slower below it; the two
are within run-to-run variance at the largest M.  If a deployment is
prefill-only at M ≥ 2048, `VK_MOE_PF_VARIANT=2` is the marginally better
choice; 16-wide is the better single default.
