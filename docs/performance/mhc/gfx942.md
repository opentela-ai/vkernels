# mhc — Multi-head hybrid-attention pre/post (AMD gfx942, MI300A)

Latency + roofline characterization of the two GLM-5.3-Flash /
DeepSeek-V3 MHC kernels in `src/c/vkernels/kernels/mhc.{cpp,hip}`
(issue #51 part 2) — the pre-attention stage-0 GEMM + squared-sum and the
post-attention combine, whose tilelang forms JIT-abort on gfx942 (dynamic
shared > 64 KB non-optin cap), so there is **no tilelang baseline delta
measurable on this hardware**.

$$\text{pre: } \text{out}[n,o] = \sum_h x[n,h]\,\text{fn}[o,h],\quad \text{sqrsum}[n] = \sum_h x[n,h]^2$$

$$\text{post: } \text{out}[n,j,h] = c[n,j]\,d[n,h] + \textstyle\sum_k a[n,k,j]\,b[n,k,h]$$

**Implementation under test** (see [`docs/kernels/mhc.md`](../../kernels/mhc.md)):
CPU fp32 oracles (always compiled) + HIP kernels using *static* shared
memory sized to fit MI300A's 64 KB non-optin cap (no
`hipFuncSetAttribute` opt-in, no `hidden_block 256 -> 128` patch):

  * `mhc_pre_gemm_sqrsum` — one block per **token** (`grid(num_tokens)`),
    the block's threads split the `hc_mult3` output columns, staging
    `x` once through a static bf16 shared buffer; fp32 accumulation of
    both `out` and `sqrsum`.
  * `mhc_post` — one block per `(token, output head j)`
    (`grid(num_tokens, hc)`), fp32 accumulators, bf16 store.

## Correctness (on the bench node)

Device-vs-oracle **11/11 PASS** (5 pre rows incl. the GLM-5.3
`hc_hidden=16384` and the wider `28672` branch, 6 post rows incl.
`hidden=4096/7168`): pre max_rel ≤ 2.0e-5 (fp32 storage), post max_rel
≤ 3.9e-3 (the documented bf16 round-trip residual).

## Workload

GLM-5.3 MHC shapes: `hc_mult=4, hidden=4096 → hc_hidden=16384,
hc_mult3=24` (decode `n=1` and a 7-token micro-batch) and the wider
`hidden=7168 → hc_hidden=28672` branch. Roof: 1307 TFLOP/s bf16,
5300 GB/s HBM3, ridge ≈ 247 FLOP/B.

## The pre kernel is single-block-bound at decode; post is noise

  * **`mhc_pre_gemm_sqrsum` launches one block per token** — at decode
    (`n=1`) the entire GEMM runs on **1 of 228 CUs**, streaming the
    1.5 MB `fn` matrix through one block: 5.8 GB/s = 0.1% of the HBM
    roof (the working set is L2-resident; the block is latency-bound on
    the serial `hc_hidden` walk per output column, and the baseline
    re-streams `fn` per column un-coalesced — the tiled, swizzled-shared
    follow-on's target).
  * **n=7 costs the same as n=1** (281 vs 278 µs): the +6 blocks add
    parallelism for free; per-token marginal cost is ~0.4 µs once the
    one-block floor (≈ 270 µs) is amortized.
  * **Serving takeaway**: pre is ~0.28 ms per layer per decode step at
    GLM-5.3-Flash — comparable to the DSA indexer stage and worth a
    split-token/parallel-column redesign, but far below the sparse
    forward's decode cost (see [`../dsa/gfx942.md`](../dsa/gfx942.md)).
  * **`mhc_post` is below the event-timer floor at every serving shape**
    (< ~0.5 µs): with `hc=4, hidden=4096` the kernel moves ~0.5 MB in
    4 blocks — effectively free; no optimization warranted.

## Caveats and notes

  * **Clocks.** `rocm-smi --setperflevel high` is not permitted on this
    cluster; idle sclk was 95–96 MHz. Medians over ≥ 20 reps with CV <
    3% are stable, but absolute µs are upper bounds; ratios and scalings
    are the robust signals.
  * **`<res` rows.** Single-launch `hipEventElapsedTime` cannot resolve
    sub-µs kernels on MI300A (~0.5 µs event floor + dynamic-sclk domain
    changes); the `mhc_post` serving shapes and the n=1 tiny-control row
    print `<res`/0.0. If a precise post number is ever needed, batch
    2000 launches per sample as `bench_dsa_kpool.hip` does.
  * **The 28672-wide pre row runs within the static-smem budget** (56 KB
    < 64 KB non-optin cap) — this is the shape the tilelang path cannot
    even JIT; measured here with no `hidden_block 256 -> 128` patch.
  * Same-build caveat as the DSA doc: the WIP tree carries the in-flight
    GB10 CUDA-port refactor; the gfx942 MHC path is untouched by it.

## Journal

Benchmarked the issue-#51 part-2 MHC pre/post kernels on CSCS beverin
(nid002664, MI300A) alongside the DSA forward (one shared run script,
`run_dsa_mhc_bench_mi300.sh`). Correctness was green on the first full
run (11/11) after the DSA-side tiny-shape fix. The numbers say: the
kernels are correct-but-underparallelized rather than kernel-bound —
pre launches one block per token, so decode GEMM work sits on a single
CU at 0.1% of the HBM roof (~278 µs/layer), while post is sub-µs and
effectively free. No tilelang baseline exists on gfx942 (JIT abort), so
the delta column is n/a by construction; the honest comparison is the
sglang-side alternative of patching tilelang's `hidden_block 256->128`,
which these HIP kernels make unnecessary. Future work: split the pre
kernel's output columns across more blocks (or batch tokens per block)
to lift the one-CU floor, and re-measure once the cluster permits
pinning clocks.

## Issue #79 — output-column split + NSLICE blocked-order ladder (nid002706, 2026-09-17)

Raw log: [`beverin-mhc-i79-nslice-ladder.log`](beverin-mhc-i79-nslice-ladder.log)
(job `vk-i79-parity`, Slurm 640390, branch `issue-79-mhc-pre-col-split` @
`e4e590c`). Two changes under test:

  * **Column split** (`bfe9e1b`): `mhc_pre_gemm_sqrsum` launches
    `grid(num_tokens, hc_mult3)` — one block per (token, output column) —
    so decode is no longer ONE block on 228 CUs. The `out` chain stays the
    oracle's strict sequential fp32 walk (tid 0), made bitwise-exact by an
    **explicit single-rounding `fmaf` on BOTH the oracle (`std::fma`) and
    the device (`fmaf`)** (`e4e590c`) — agreement no longer depends on
    either compiler's implicit `-ffp-contract` mode (the classic gfx942
    trap: `contract(off)` two-rounding vs the oracle's one-rounding FMA was
    the n=7 1.19e-5-rel residual).
  * **Blocked-order variant** (`6cb2fd6`+): `mhc_pre_gemm_sqrsum_blocked`
    splits each column's chain across NSLICE threads (contiguous slices,
    in-order combine) to break the serial-chain latency floor. NSLICE is
    swept {256,128,...,1} by the test (drift) and the bench (latency).

### Correctness (device vs CPU oracle, 0 failures)

| row | strict split | blocked ns=256 | ns=8 | ns=1 |
|---|---|---|---|---|
| n=1 hc_hidden=16384 | rel 9.7e-6 PASS | 2.8e-5 PASS | 1.4e-5 PASS | 9.7e-6 PASS |
| n=7 hc_hidden=16384 (gate row) | rel 1.9e-5 PASS | **1.08e-4 FAIL** | 7.1e-5 PASS | 1.9e-5 PASS |
| n=1 hc_hidden=28672 | rel 1.8e-5 PASS | 5.3e-5 PASS | 4.2e-5 PASS | 1.8e-5 PASS |

All 11 rows PASS the unchanged `PRE_THRESH = 1e-4` in the strict split.
The residual on every strict/ns=1 row is the **sqrsum tree** (order-free
cooperative reduction, ns-independent: abs is byte-identical across ns at
each shape), inside the documented <= 2e-5 envelope — the `out` chain
itself is bitwise-exact at ns=1 by construction. The blocked variant's
extra drift (~0.7-1.2e-4 on the n=7 row, NON-monotone in NSLICE) is fp32
associativity regrouping noise of the same order as the oracle's own
rounding-path deviation from the exact sum (~1.03e-4 on this row): only
ns=8/ns=4 clear 1e-4 on this seed, and nothing above ns=1 clears 2e-5.

*ns=256/128 hit the known ROCm 6.3 all-zero-event-window quirk (see
`bench_us` in `bench_mhc.hip`); extrapolating the measured
latency ∝ chain-length curve (418 µs / 16384-chain) puts them at ~6-13 µs.

Findings:

  * **The issue's core claim is confirmed**: the pre kernel moves 2.0-2.2 GB/s
    = 0.04% of the 5300 GB/s HBM roof at decode; the strict column split
    alone (24 blocks x 1 active chain thread) does NOT lift the
    latency floor — the serial hc_hidden FMA chain (~40+ cyc/iter on the
    in-order LDS->fmaf dependency) dominates, and at 815 µs the strict
    split is in fact slower than the pre-#79 one-block layout (whose 24
    un-coalesced global chains overlapped more cheaply).
  * **The blocked-order ladder is the actual fix**: latency ∝
    16384/NSLICE (25.3 µs per 256-chain at ns=64, scaling cleanly down to
    the 16384-chain 418 µs at ns=1). ns=16 (44 µs) is the first point under
    the 50 µs/layer serving target; ns=64 reaches 26.6 µs.
  * **But gate compliance and speed trade off against each other**: under
    the unchanged oracle-chain 1e-4 gate, only ns=8 (68.8 µs) is both
    gate-PASS and meaningfully faster on this seed. Any NSLICE > 1 sits at
    the oracle's own associativity-deviation scale (~1e-4), so the gate —
    not the kernel — is the binding constraint.

### Recommendation

  * Ship `e4e590c` (strict split + explicit-fma oracle/device agreement) as
    the correctness path: bitwise-exact `out`, 0 failures, unchanged gate.
  * Recommended NSLICE **if the gate is revisited**: 64 (26.6 µs decode,
    10.5x vs pre-#79, drift 1.1e-4 = the oracle's own fp32 deviation from
    the exact sum; an fp64-reference or blocked-aware gate would admit it).
    **If the 1e-4 oracle-chain gate is kept**: NSLICE=8 (68.8 µs, 4x) is
    the fastest measured point that passes, with thin margin.
  * The 50 µs decode target is reachable only at ns>=16, i.e. only with a
    gate change. **-> Done in issue #138 (see the section below): the
    conditioning-normalized fp64-reference gate admits ns>=16 and the
    decode shape measures 43.5 µs (ns=16) / 30.8 µs (ns=32).**

### Remaining risk

  * Blocked-variant drift is **seed-dependent** (ns=2/16/32 FAIL 1e-4 on
    this seed while ns=4/8 pass): gate margin, not a stable ordering.
  * ns=256/128 latency rows are extrapolated (event-timer quirk), and
    clocks are not pinnable on this cluster (same caveat as above);
    absolute µs are upper bounds, ratios robust.
  * sqrsum remains a tree reduce (1.8-1.9e-5 rel, inside 2e-5 but not
    bitwise); if bitwise sqrsum is ever required it needs the same
    explicit-chain treatment at a latency cost.

## Issue #138 — fp64-reference gate revision: NSLICE≥16 admissible, ≤50 µs/layer met (nid003026, 2026-09-18)

Raw log: [`beverin-mhc-i138-gate.log`](beverin-mhc-i138-gate.log)
(job `vk-i138b`, Slurm **641091**, branch `issue-138-mhc-pre-f64-gate` @
`4fed61c`+docs; survey predecessor `vk-i138`, Slurm **641058**).
Script: `meta/scripts/run_issue138_mhc_gate_mi300.sh`.

### Why the #79 oracle-chain gate had to go

The gate under #79 compared the device fp32 `out` against the fp32 oracle's
strict sequential chain at `max_rel < 1e-4`. The multi-seed survey (5 seeds
× NSLICE {256..1} × 3 GLM shapes, plus the strict split) shows that gate is
untenable in BOTH directions:

  * **It fails the SHIPPED strict kernel on other seeds.** Seed 2, n=7
    hc_hidden=16384: strict split `out` max_rel = 1.02e-4 → FAIL (seed 1:
    1.9e-5 PASS). The fp32 sequential chain's own deviation from the exact
    (fp64) sum is seed-dependent at the 1e-4 scale — the "gate margin" was
    never a kernel property.
  * **It fails provably-correct blocked orders on ~every seed** (the #79
    ns=2/16/32 observation, reproduced across seeds 2–5).
  * **Blocked orders are usually MORE accurate than the oracle**: e.g.
    seed 2 n=7 ns=256 sits 4.96e-4 rel from the oracle chain but only
    3.3e-5 rel from the fp64 exact sum. The legacy gate was punishing the
    blocked kernel for the oracle's own rounding error.

Root cause: fp32 accumulation of this dot product — in ANY order —
random-walks to ~1e-6..4e-4 rel vs fp64 on heavily-cancelled outputs
(5-seed measured range). No fixed relative threshold below ~1e-3 is
seed-stable, and 1e-3 would be far too loose.

### The revised gate (default policy)

Conditioning-normalized fp64-reference comparison, per element:

    |got - ref64| <= K * eps32 * sum_h |x_h * fn_h|     (out)
    |got - ref64| <= K * eps32 * sum_h  x_h^2           (sqrsum)

`ref64` = `mhc_pre_gemm_sqrsum_cpu_f64` (new fp64 CPU oracle),
`eps32 = FLT_EPSILON`, **K = 256** (`VK_MHC_F64_K` env override). The
normalization is the standard a-priori fp32 accumulation-error scale, so
the gate is **order-invariant** (every correct accumulation order sits at
the same envelope) and it is TIGHTER than the legacy 1e-4 wherever the
output is well-conditioned. The legacy strict-1e-4 oracle-chain gate
remains available verbatim via `VK_MHC_STRICT_GATE=1`.

Measured on MI300A (job 641091, 5 seeds, NSLICE 1..256, all three shapes,
strict + blocked + ns=1):

| statistic | clean kernels (all rows, all seeds, all NSLICE) | corrupted kernel (fn row +1, negative control) |
|---|---|---|
| normalized fp64 error (out) | **max 0.9** | 3.2e5 – 4.1e5 |
| normalized fp64 error (sqrsum) | max 0.7 | ≤ 0.7 (sqrsum path uncorrupted) |

i.e. **~280× headroom** between the worst clean row and K=256, and the
corrupted control sits **>5 orders of magnitude** above the gate — it
FAILs on every seed. A single dropped/shifted fmaf term perturbs an output
by ~1/(K·eps) ≈ 515 normalized units, still above the gate. Verdict:
default-gate run **PASS (0 failures)** including the strict split and all
blocked NSLICE on every seed; corrupted control FAIL 5/5 (as required).
Policy test mirror (numpy-only, bare env):
`tests/python/test_mhc_gate_policy.py`.

### Acceptance status

  * [x] Gate revised so NSLICE≥16 is admissible (conditioning-normalized
    fp64-reference gate; strict 1e-4 oracle-chain gate kept via
    `VK_MHC_STRICT_GATE=1`) — hardware-verified, 5 seeds.
  * [x] GLM-5.3 decode shape ≤50 µs/layer at an admissible NSLICE —
    measured 43.5 µs (ns=16) / 30.8 µs (ns=32).
  * [x] Correctness vs CPU oracle: max_rel within the new gate on every
    seed/NSLICE (worst clean normalized error 0.9 vs K=256); gate policy
    documented here and in `docs/kernels-reference.md`.
  * [x] Perf record updated (this file + `docs/kernels-reference.md`).

### Remaining risk

  * K=256 is pinned from THIS generator's 5-seed envelope (max 0.9). Other
    input distributions shift the envelope by O(1) factors, not orders —
    the normalization tracks the conditioning automatically. If a future
    shape/seed exceeds K, `VK_MHC_F64_K` adjusts without a code change
    (and the raw f64 rel is printed per row for diagnosis).
  * ns=64/128/256 latency rows remain event-timer-quirk-bound (ratios
    robust; ns=32 is the fastest fully-measured admissible point).
  * Clocks not pinnable on this cluster (unchanged caveat): absolute µs
    are upper bounds, ratios robust.
