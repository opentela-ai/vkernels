# dsa-kpool — paged tail-cache pool compress/write (AMD gfx942, MI300A)

A latency + roofline characterization of the DSA kpool-cache kernels in
`src/c/vkernels/kernels/dsa_kpool.{cpp,hip}` (issue #60) — the bookkeeping
stage that maintains the **live tail** (a per-request ring of the most
recent tokens) and **compresses each completed pool** into the paged cache
for the DSA sparse attention path:

$$\text{out}[pool] = H_{128}\left(\frac{\sum_{p=0}^{P-1} \exp\!\big(s_p + ape[p] - \max_j (s_j + ape[j])\big)\, k_p}{\sum_{p=0}^{P-1} \exp\!\big(s_p + ape[p] - \max_j (s_j + ape[j])\big)}\right)$$

Two kernels, one warp-group (64 threads) per pool/request:

  * **`dsa_kpool_assemble`** (prefill) — gathers each pool's `pool_size`
    slots from the chunked cache + live tail, two-pass softmax-weighted
    mean over the pool, 128-point Hadamard, writes the compressed K into
    the paged pool slot.
  * **`dsa_kpool_decode_update`** (decode) — unconditionally writes the
    current token's key/score into the live-tail ring (in-place, masked
    no-op when the row is invalid); when the token closes the pool
    (`pos % pool_size == pool_size-1`) it compresses the complete pool
    into the paged out slot exactly like the prefill path.

Shapes follow GLM-5.3-Flash / DeepSeek-V3: `head_dim = 128` bf16 keys and
scores, fp32 `ape` positional gate, `pool_size ∈ {4, 8}`,
`tail_size ∈ {64, 128}`, `slots_per_page ∈ {8, 16}`.

## Correctness (on the bench node)

Host oracle 16/16; device-vs-oracle **14/14 PASS** (prefill 7, decode 7).
The compressed-K output carries only the bf16-store residual
(`max_rel ≈ 3.4e-3`, tolerance 2e-2, identical magnitude to the prefill
rows); the in-place live-tail update is an exact bf16 copy
(`max_rel = 0`).

Two harness bugs were found and fixed while benchmarking (see Caveats):
a device-side write-write race in the generated decode data, and vacuous
compress coverage (`out` was zero on both sides). The decode rows now
exercise both the compress and the tail-write paths.

## The binding constraint is LAUNCH/OCCUPANCY, not HBM or compute

  * **Arithmetic intensity 1.3–1.5 FLOP/B** — ~180× below the ~247 FLOP/B
    ridge; the kernel can never be compute- or HBM-bound at these shapes.
  * **Peak effective bandwidth 214 GB/s = 4.0% of the HBM roof** (bs=512,
    ps=8); peak 0.27 TFLOP/s = 0.02% of the compute roof.
  * **Latency is nearly flat from 1 to 128 warp-groups** (10.7 → 11.2 µs
    prefill; 11.7 → 12.2 µs decode): 128× more parallel work costs ~0.5 µs.
    The marginal cost beyond the floor is **~15 ns per request**; even at
    bs=512 the whole step is ~20 µs.
  * **Empty-kernel control**: a do-nothing 64-thread kernel launched
    back-to-back measures **2.8 µs/launch** on this node — so of the
    ~11 µs at bs=1, roughly a quarter is HIP dispatch and the rest is
    kernel execution under the dynamic clock (see caveat below). In
    serving terms the entire kpool step is 12–22 µs — noise against a
    ms-scale decode forward pass, and <1% of step time even if invoked
    per layer.

## Caveats and notes

  * **Timing methodology.** These kernels are sub-µs at small shapes;
    single-launch `hipEventElapsedTime` returns corrupted 0.0 ms on
    MI300A (dynamic-sclk domain change between configs + ~0.5 µs event
    resolution), which first showed up as `us=0.00, TFLOP/s=inf` rows.
    The bench therefore batches **2000 launches per timed sample** and
    divides (re-launching is idempotent: the compress reads slots other
    than the single live-tail write), with a warmup burst + sync before
    the first timed event and an implausibility retry, mirroring
    `bench_dsa_topk_logits.hip`.
  * **Clocks.** `rocm-smi --setperflevel high` is not permitted on this
    cluster; idle sclk was ~104 MHz. Batched launches keep the GPU busy
    but the governor's boost during the measurement is not pinned, so
    absolute µs are an upper bound; the flatness and per-request scaling
    are the robust signals.
  * **Harness race (fixed).** The decode test originally mapped several
    batch entries onto one request tail via `rpi[r] = r % n_reqs` with
    `pos[r] = r % sl[r]`; at batch=16 entries r=0 and r=8 both resolved
    to (req 0, phys 0) — a same-slot write-write race between two blocks
    that the serial CPU oracle cannot model (device result depended on
    block scheduling, failing ~90% of runs with `ts[r=2.91]`). Fixed by
    giving every valid entry its own tail (`n_reqs >= batch`), matching
    the real sglang contract of one decode entry per running request.
  * **Vacuous compress coverage (fixed).** With the original
    `pos[r] = r % sl[r]`, `slot` was never `pool_size-1` for a valid
    entry, so the decode compress output was never compared (both sides
    wrote nothing). Valid entries now alternate pool-closing / mid-pool,
    and `out` shows the expected ~3.4e-3 bf16 residual.
  * **Re-launch idempotence.** The batched timing relies on the decode
    kernel writing the live-tail slot that the compress never reads
    (`is_current` substitution), so repeating a launch on constant
    inputs reproduces the same state.

## Journal

Benchmarked the issue-60 kpool kernels on CSCS beverin (MI300A, gfx942)
after bristen's idle GPU nodes proved unbootable. Getting a trustworthy
number took three fixes: (1) the first run printed `inf` TFLOP/s because
single-launch event timing cannot resolve a sub-µs kernel on MI300A —
switched to 2000-launch batched samples; (2) a node-dependent
correctness failure (bs=16 decode, `ts[r=2.91]`) looked like a kernel
bug but a 30-iteration argmax repro pinned it to a harness-generated
write-write race (two batch entries, same tail slot), fixed by making
the decode data respect the one-entry-per-request contract; (3) the same
repro revealed the decode compress path had never been checked at all
(`out` zero on both sides) — the harness now alternates pool-closing and
mid-pool entries. Final state: 14/14 device rows pass (5× repeat
verified), and the benchmark shows the kernels are launch/occupancy
bound bookkeeping ops — 12–22 µs per step at serving shapes, ~15 ns per
request marginal cost, 4% of the HBM roof at worst. Future work: pin
clocks if the cluster ever permits `setperflevel`, and re-measure the
dispatch floor on a quieter node.
