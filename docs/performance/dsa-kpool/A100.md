# dsa-kpool — paged tail-cache pool compress/write (NVIDIA A100, sm_80)

A latency + roofline characterization of the DSA kpool-cache kernels on an
**NVIDIA A100-SXM4-80GB**, obtained by compiling the same HIP device sources
(`src/c/vkernels/kernels/dsa_kpool.{cpp,hip}`) with **nvcc as CUDA** — no ROCm
anywhere on the machine. This is a cross-architecture portability check and a
second data point for the launch-bound analysis in [gfx942.md](gfx942.md);
the kernel math, oracle and harness are identical (see that file for the
formula and contract).

## The port (HIP-on-NVIDIA)

Three small, ROCm-build-neutral changes let the `.hip` sources compile under
`nvcc -x cu` (CUDA 12.6, `sm_80`, gcc 13.3 via the CSCS `prgenv-gnu/24.11:v1`
uenv):

  * `src/c/vkernels/kernels/cuda_compat/hip/hip_runtime.h` — a ~70-line shim
    that maps the (small) HIP API surface the sources use onto the CUDA
    runtime API (`hipMalloc→cudaMalloc`, events, props, ...), neutralizes
    `__host__/__device__` for host TUs, provides the std headers the real HIP
    header transitively includes, and maps `gcnArchName→name` so the
    device-detection code keeps compiling. It `#error`s if ever picked up by
    a ROCm build.
  * `moe_device.hip` — the gfx942-only MFMA inline-asm helper is now guarded
    by `#if defined(__gfx942__)||...` (nothing in the kpool path uses it).
  * `bench_dsa_kpool.hip` — device detection is by compute capability
    (`p.major == 8 && p.minor == 0`) rather than a name substring, with a
    loud `stderr` warning (placeholder roofs) on any unrecognized device.

No changes to the kernels themselves — the kpool code uses no gfx942-specific
intrinsics. The build is the normal CMake build: on a CUDA-only node,
`CudaSupport.cmake` finds nvcc and `src/c/CMakeLists.txt` compiles the kpool
`.hip` sources as CUDA (`LANGUAGE CUDA` + the shim include dir, per-source
`VKERNELS_HAS_HIP=1`); `meta/benchmarks/CMakeLists.txt` adds the two
executables the same way. `meta/scripts/build_dsa_kpool_a100_cuda.sh` is
just the srun/uenv wrapper around `cmake` + the two binaries.

## Correctness (on the bench node)

Device-vs-host-oracle **14/14 PASS** (prefill 7, decode 7), CUDA 12.6 / sm_80.
The compressed-K output carries only the bf16-store residual
(`max_rel ≈ 3.4e-3`, tolerance 2e-2 — identical magnitude to the gfx942 run);
the in-place live-tail update is an exact bf16 copy (`max_rel = 0`). Same
harness (including both decode coverage fixes from the gfx942 campaign), so
both the compress and tail-write paths are exercised.

## A100 vs MI300A — same conclusion, different constants

| shape (decode) | A100 µs | MI300A µs | ratio |
|---------------:|--------:|----------:|------:|
| bs=1, ps=4 | 8.6 | 11.7 | 0.74 |
| bs=512, ps=4 | 12.1 | 19.6 | 0.62 |
| bs=1, ps=8/t128 | 11.5 | 13.5 | 0.85 |
| bs=512, ps=8/t128 | 15.7 | 21.5 | 0.73 |

  * **A100 is 0.6–0.85× the MI300A absolute latency at every shape** — the
    floor is lower (6.0 vs 10.7 µs prefill bs=1) and the marginal cost per
    request is ~7 ns (vs ~15 ns on MI300A).
  * **The launch-bound verdict is architecture-independent.** Arithmetic
    intensity 1.3–1.5 FLOP/B sits ~6.5× below the A100's much lower ridge
    (~10 FLOP/B) and ~180× below MI300A's (~247 FLOP/B) — but both GPUs are
    still nowhere near either roof: peak effective bandwidth 294 GB/s =
    14.5% of the A100 HBM roof (vs 214 GB/s = 4.0% on MI300A), and the
    latency stays nearly flat from 1 to 256 warp-groups (6.0 → 8.0 µs
    prefill ps=4; 8.6 → 9.9 µs decode ps=4) before the bs=512 tail.
  * **Caveat on the comparison**: the MI300A µs are upper bounds (unpinned
    idle sclk ~104 MHz, see gfx942.md caveats), while the A100 boosts clocks
    quickly during the 2000-launch bursts, so part of the gap is measurement
    environment, not silicon. The direction (both are launch-dominated
    bookkeeping ops, 6–22 µs per step, noise against a ms-scale decode
    pass) is the robust signal, and it holds on both.
  * No empty-kernel dispatch-floor control was run on A100 this time
    (MI300A's was 2.8 µs/launch); given the 6.0 µs prefill floor, a similar
    quarter-to-third share is dispatch. Future work: add the control to
    this script.

## Caveats and notes

  * **Timing methodology** is the same as gfx942: 2000-launch batched
    samples, warmup burst, implausibility retry (CUDA `hipEventElapsedTime`
    resolution is ~0.5 µs, single launches of sub-µs kernels round to 0).
  * **Clocks not pinned** (`nvidia-smi -lgc` not attempted on this cluster);
    repeat run of the whole job reproduced every row within ~1–2%
    (e.g. decode bs=512 ps=8: 15.65 vs 15.44 µs).
  * **The `hipEvent_t`/`hipStream_t` types and `<<<>>>` launches** translate
    1:1 under the shim; the only source-level touch beyond the shim/mfma
    guard was the A100 roofline row in the bench.
  * **What this run does NOT characterize**: tensor-core or fp8 paths, RCCL,
    and the MI300A-specific shared-memory/L2 behavior. It is a portability +
    launch-latency data point, not the issue-#60 serving-target benchmark
    (that remains gfx942.md).

## Journal

Ported the issue-60 kpool HIP kernels to NVIDIA A100 (bristen) after
confirming bristen's GPU nodes are A100-SXM4-80GB with no ROCm — CUDA 12.6
arrives via the CSCS `prgenv-gnu/24.11:v1` uenv (`--view=default` exposes
nvcc). The port took three edits, none touching kernel math: a ~70-line
`hip/hip_runtime.h` shim mapping the used HIP API onto CUDA (plus the std
headers the real HIP header transitively provides — first compile failed on
`std::string`), a guard around `moe_device.hip`'s MFMA inline asm
(uncompilable register-asm syntax under nvcc, unused by kpool), and an A100
roofline row in the bench device table. The MFMA guard needed a pass-aware
shape: the function *signature* must stay visible in HIP host passes (they
type-check `__global__` callers — a fully-`#if`'d definition broke a
beverin micro-test), while only the register-asm *body* is AMD-only; the
gfx942 device pass was verified to define `__gfx942__` (`--cuda-device-only`),
unsupported AMD device passes `#error`, and the nvcc build compiles an empty
stub. First full job: 14/14 device correctness vs the host oracle with
residual magnitudes identical to MI300A (bf16-store only, live-tail copy
exact), and a benchmark that lands 0.6–0.85×
the MI300A absolute latencies with the same launch-bound shape. Rerun with
the roof label corrected to fp32 (A100 rows do CUDA-core math) and saved the
raw log; further full runs reproduced all rows within ~2%.

Post-review tightening: the build moved from a hand-rolled nvcc script into
the normal CMake CUDA branch (same flags, one source of truth), device
detection switched from a name substring to compute capability with a loud
placeholder warning on unknown devices, and the stale "no CMake changes"
claim above was retired.
