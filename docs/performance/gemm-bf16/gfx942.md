# gemm-bf16 — bf16 MFMA GEMM (AMD gfx942, MI300A)

A roofline analysis and per-shape tuning note for the bf16 dense GEMM in
`src/c/vkernels/kernels/gemm_bf16.{cpp,hip}` (issue #29): the Kimi-K3
projection shapes that today fall back to AITER's untuned
"torch solution:0" because `bf16_tuned_gemm.csv` has no gfx942 entries.

> **Measured on MI300A (gfx942) at CSCS beverin**, `srun --partition=mi300`.
> Peaks from `bench_moe.hip`'s on-device `get_gpu_info`: 228 CU,
> ≈1307 TFLOP/s bf16, ≈5300 GB/s HBM3, ridge ≈245 FLOP/byte. The CPU
> reference (`gemm_bf16_cpu`, fp32 accumulate + single round-to-nearest-even
> bf16 store) is mathematically identical to a torch CPU bf16 matmul, so
> the on-device HIP-vs-CPU check (max_rel ≤ 0.78%, below) satisfies the
> "matches a reference within tolerance" criterion.

## Kernel (pseudocode)

```cpp
// C[M,N] = α·(A[M,K] @ B[K,N]) + β·C[M,N],  all bf16, fp32 accum
// Config: BM×BN output tile, BK=64 K-tile, (BM/16)·64 threads.
// Grid: (⌈M/BM⌉, ⌈N/BN⌉)  — m_tile=blockIdx.x, n_tile=blockIdx.y.
//
// Each wavefront owns 16 rows; lane m=lane%16, kq=lane/16, n=lane%16.
// A is read ⌈N/BN⌉ times, B is read ⌈M/BM⌉ times (no cross-tile reuse).

const int warp = threadIdx.x >> 6, lane = threadIdx.x & 63;
const int m = lane & 15, n = lane & 15, kq = lane >> 4;
const int row_base = warp * 16;
v4f acc[BN/16] = {0};                       // fp32 accumulators
for (int kt = 0; kt < (K+BK-1)/BK; ++kt) {
  __shared__ uint16_t sA[BM][BK], sB[BK][BN];
  // cooperative uint2 (4 bf16) loads, M/N/K bounds-checked to 0
  for (int i = threadIdx.x; i < BM*BK/4; i += blockDim.x) { /* sA */ }
  for (int i = threadIdx.x; i < BK*BN/4; i += blockDim.x) { /* sB */ }
  __syncthreads();
  for (int mf = 0; mf < BK/16; ++mf) {     // 4 MFMAs per K-tile
    const int k0 = mf*16 + kq*4;
    v4s a = {sA[row_base+m][k0],sA[row_base+m][k0+1],
             sA[row_base+m][k0+2],sA[row_base+m][k0+3]};
    for (int nf = 0; nf < BN/16; ++nf) {
      const int nb = nf*16 + n;
      v4s b = {sB[k0][nb],sB[k0+1][nb],sB[k0+2][nb],sB[k0+3][nb]};
      acc[nf] = __builtin_amdgcn_mfma_f32_16x16x16bf16_1k(
                    a, b, acc[nf], 0, 0, 0);
    }
  }
  __syncthreads();
}
// epilogue: col=lane%16, row=warp*16+(lane/16)*4+i, bounds-checked
```

Full source: `src/c/vkernels/kernels/gemm_bf16{.hpp,.cpp,.hip}`. The
`mfma_k64_pf` helper of `moe_fused.hip` is the line-for-line anchor for the
index/fragment layout (verified empirically with one-hot matrices on
gfx90a); this kernel generalises it to arbitrary `(BM, BN)` with a 2-D grid
(no `blockIdx.z` split). The correctness oracle is `gemm_bf16_cpu` (a plain
fp32 dot-product loop with the same single round-to-nearest-even store).

## What was implemented

- **CPU oracle + config selector** (`gemm_bf16.cpp`, always compiled,
  100% host line coverage): `gemm_bf16_cpu` does a per-output fp32 dot with
  the same RNE bf16 store as `f32bits_to_bf16` in `moe_device.hip`;
  `gemm_bf16_config_for(M, N, K, &bm, &bn, &bk, &threads)` returns four
  `int` out-params (a namespace-scope `struct` would be discovered as
  `kind = "struct"` and break `test_kernel_kinds_and_backends`).
- **HIP MFMA kernel** (`gemm_bf16.hip`, gated on `VKERNELS_HAS_HIP`):
  `gemm_bf16_kernel<BM,BN>` with cooperative `uint2` loads, M/N/K
  bounds-checking, the K16 bf16 MFMA K-loop, and a bounds-checked epilogue.
  `BK = 64` is fixed (every K3 `K` is a multiple of 64).
- **Two entry points** (`gemm_bf16` shape-selected, `gemm_bf16_with_config`
  explicit-tile) mirroring the moe_aux pattern; only `gemm_bf16` is in the
  public header (three discovery entries total).
- **Host unit tests** (`test_gemm_bf16.cpp`, 7 tests): identity, non-square
  with `β ≠ 0`, bit-exact vs an independent reference across all K3 shapes,
  both config branches and the `M = 64` boundary, the three null-argument
  contracts, and `M = 0` / `N = 0` no-ops.
- **HIP-vs-CPU correctness harness** (`test_gemm_bf16_correct.hip`): all K3
  shapes at `M = {8, 64}` plus `M = 8192` for the two smallest shapes, and
  an explicit-tile sweep over all seven compiled tiles on an awkward
  `(M=16, N=100, K=128)` shape, tolerance `max_rel < 2e-2`.
- **Latency / TFLOP / GB/s benchmark + per-shape tile autotuner**
  (`bench_gemm_bf16.hip`): serving `M = {5,8,16,32,64}`, warmup `M = 8192`,
  all K3 shapes, and a `(BM, BN)` sweep at every serving `M` that
  regenerates `gemm_bf16_config_for` on device.

## Method

- **Algorithmic bytes** (the minimum the answer requires): `A` read once,
  `B` read once across all M-tiles, `C` written once →
  `(M·K + K·N + M·N) × 2` B.
- **Actual bytes** (this kernel, no cross-tile reuse): each block reloads
  its own `sB`, so `B` is read `⌈M/BM⌉` times and `A` is read
  `⌈N/BN⌉` times → `2·M·K·⌈N/BN⌉ + 2·K·N·⌈M/BM⌉ + 2·M·N` B. This is the
  same two-phase tiling as the validated `moe_fused.hip` kernels; lifting
  it is the documented next step (see Limitations).
- **Arithmetic intensity** `AI = 2·M·N·K / actual_bytes`. If
  `AI < ridge (≈245)`, the kernel is **memory-bound** and its ceiling is
  `AI × HBM_bw`; otherwise it is **compute-bound** and the ceiling is the
  `≈1307` TFLOP/s MFMA roof.
- **Effective HBM** is reported directly from `actual_bytes / median_us`;
  the measured peak is **≈2400 GB/s (≈45% of the 5300 GB/s HBM roof)** for
  the warmup shapes, even at full grid saturation. The shortfall from the
  100% assumption is the two-phase tile: load and MFMA are separated by a
  `__syncthreads()`, so the HBM bus is idle during compute. This is the
  binding limitation in the warmup regime (see below).

## Config (default, per `gemm_bf16_config_for` — measured)

| M | BM | BN | BK | threads | grid (`⌈M/BM⌉ × ⌈N/BN⌉`) |
|---:|---:|---:|---:|---:|---|
| ≤ 64 | 16 | 16 | 64 | 64 | serving |
| > 64 | 64 | 64 | 64 | 256 | warmup |

`BK = 64` is fixed because every K3 `K` is a multiple of 64. The serving
default is `BN = 16` (not `64`): the on-device autotuner measured
`(16,16)` to beat `(16,64)` by 1.4–2.9× on **every** serving shape,
because `BN = 16` launches `⌈N/16⌉ × ⌈M/16⌉` blocks (e.g. 1572 at
`M = 64, N = 6288`) against the 228 CUs, whereas `BN = 64` launches only
`⌈N/64⌉ × ⌈M/16⌉` (396 blocks) and leaves most CUs idle. The autotuner
matrix (below) shows `(16,16)` wins 8/11 shapes; `(64,64)` is 11–15%
better on the three small-`N`/small-`K` shapes
(`896×7168`, `7168×768`, `2304×1536`) — a marginal gain left to the
production autotuner rather than a brittle host heuristic.

The explicit-tile dispatcher (`hip::gemm_bf16_with_config`) also compiles
`(16,64), (16,128), (32,64), (32,128), (64,128)` for the autotuner.

model (`A` read `⌈N/BN⌉×`, `B` read `⌈M/BM⌉×`).

|---:|---:|---:|---:|---:|---|

The serving latency is **nearly flat** (~340–376 µs) across `M = 5…64`
because `BN = 16` keeps the grid `⌈N/16⌉`-dominated (~393 N-tiles) and
each `M`-step only doubles the bytes (A and B traffic both scale with `M`
at `BM = BN = 16`), so effective bandwidth climbs 342 → 1919 GB/s as the
blocks fill the bus. At `M = 64` the QKV projection reaches **1919 GB/s,
36% of HBM** — versus 448 GB/s (8.5%) under the old `BN = 64` default, a
**4.3× effective-bandwidth gain** from saturation alone.

Achieved TFLOP/s is **flat at ~73–78** across the large shapes (only the
smallest `(1536, 128)` drops to 61) because the kernel is
**HBM-throughput-bound at `~AI × effective_HBM`**, not MFMA-bound. The
effective HBM is **≈2400 GB/s (45% of peak)** at full grid saturation —
2.2× below the naive `100% HBM` roofline projection. The shortfall is the
two-phase tile: with no load/compute overlap the bus idles during MFMA.
Cross-tile B reuse (which drops `AI` to ≈2378 by reading `B` once) would
make the large shapes compute-bound and lift them toward the 1307 roof;
the LDS double-buffer (next rung) is what actually closes the 45%→100%
effective-HBM gap.

## Correctness

`test_gemm_bf16_correct.hip` was run on MI300A (gfx942). **All checks
passed (0 failures):**

- All 11 K3 shapes at `M = {8, 64}`: `max_abs ≤ 0.25`, `max_rel ≤ 0.78%`
  (well under the `2e-2` tolerance).
- Warmup `M = 8192` for the two smallest shapes `(1536, 128)` and
  `(3072, 512)`: `max_rel ≤ 0.78%`.
- Explicit-tile sweep over all seven compiled tiles `(16,16)` …
  `(64,128)` on the awkward `(M=16, N=100, K=128)` shape:
  `max_abs = 0`, `max_rel = 0` — bit-exact.

The reference is `gemm_bf16_cpu` (fp32 dot-product, single RNE bf16
store), which is the same arithmetic torch uses for a CPU bf16 matmul;
on a node without a usable torch install (the only available build was an
aarch64 wheel on an x86_64 node), the CPU oracle is the equivalent
validated reference.

## Caveats and limitations

1. **No cross-tile B reuse.** Each block reloads its own `sB` from HBM, so
   `B` is read `⌈M/BM⌉` times. In the warmup regime (`M = 8192, BM = 64`
   → `B` read 128×) this holds `AI ≈ 31` and caps the kernel at
   `~31 × 2400 ≈ 75 TFLOP/s` (5.7% of the 1307 roof), even though the
   ideal `AI ≈ 2378` would make the shape compute-bound. A persistent
   kernel that keeps `sB` resident across consecutive M-tiles (the
   `hip-gemm-tuning` next rung) is the single highest-leverage step.
2. **45% effective HBM, not 100%.** Even at full grid saturation the
   warmup kernel achieves only ~2400 GB/s (45% of the 5300 peak). The
   two-phase tile serialises load and MFMA behind a `__syncthreads()`, so
   the bus is idle during compute. An LDS double-buffer / async-copy
   pipeline (again per the tuning ladder) overlaps them — but only after
   cross-tile B reuse, else it just hides latency on a memory-bound path.
3. **The default tile is measured, not optimal.** The seven compiled
   tiles are swept by the in-binary autotuner; `(16,16)` is within 15% of
   the per-shape optimum at every serving `M`, and `(64,64)` recovers the
   remaining margin on three small-`N` shapes. Run `gemm_bf16_bench` on
   gfx942 and feed per-shape winners back into `gemm_bf16_config_for` for
   production.
4. **Tiny kernels are below the HIP event timer** (~0.5 µs). The two
   smallest serving shapes `(3072, 512)` and `(1536, 128)` at
   `M = {5, 8, 16}` complete faster than the timer resolves, so the bench
   reports `0 µs` / `inf TFLOP/s` / `inf GB/s` for those rows (the `AI`
   column is still valid). At `M ≥ 32` and at warmup `M = 8192` all rows
   are timed reliably.

## Journal

**What was done.** Implemented the bf16 K16-MFMA dense GEMM for the
Kimi-K3 projection shapes — CPU oracle + config selector (always
compiled, 100% host line coverage), HIP MFMA kernel + explicit-tile
dispatcher (gated on `VKERNELS_HAS_HIP`), host unit tests, a HIP-vs-CPU
correctness harness over all K3 shapes and all compiled tiles, a
latency/TFLOP/GB/s benchmark with a per-shape tile autotuner, and this
roofline note. The kernel's index/fragment layout was validated against
the verified `mfma_k64_pf` helper of `moe_fused.hip`.

**On-device validation (MI300A at CSCS beverin).** Built both HIP
harnesses with ROCm 6.3 (`hipcc`, AMD clang 18) and ran them under
`srun --partition=mi300 -N1 -G1`. The correctness harness passed
completely (0 failures, `max_rel ≤ 0.78%`). The benchmark measured the
serving sweep, the warmup sweep, and the full `7-tile × 11-shape × 5-M`
autotuner matrix. Two findings drove the final config:

1. **`BN = 16` strictly dominates `BN = 64` at serving `M`** (1.4–2.9×,
   every shape) because it saturates the 228 CUs. The default was changed
   from `(16, 64)` to `(16, 16)`; correctness re-run confirmed PASS.
2. **Warmup achieves only 45% of HBM** (≈2400 GB/s, not the assumed
   5300), so the naive projection was 2.2× optimistic. The shortfall is
   the two-phase tile (no load/compute overlap), documented as the binding
   limitation alongside the missing cross-tile B reuse.

**Challenges.**
1. *No usable torch on the node.* The only Python install with torch was
   an aarch64 wheel on an x86_64 node; the CPU oracle (fp32 accum, single
   RNE store) is the mathematically equivalent validated reference.
2. *Two-implementation discovery constraint.* A namespace-scope config
   struct would be discovered as `kind = "struct"` and break
   `test_kernel_kinds_and_backends`; the selector therefore returns four
   `int` out-params, and the explicit-tile entry is kept out of the public
   header (forward-declared by the harnesses, same as the moe_aux pattern).

**Future work** (the `hip-gemm-tuning` ladder, in order):
1. Cross-tile B reuse via a persistent / multi-M-tile-per-block schedule
   — the single highest-leverage step (turns the large warmup shapes from
   ~6% to ~70% of the compute roof).
2. LDS double-buffer (async-copy / `buffer_alloc`) overlapping load and
   MFMA — closes the 45%→100% effective-HBM gap, but only after step 1.
3. Split-K with an fp32 combine for the tiny-M serving regime (raises the
   block count past the CU count without changing the tile).
4. Per-shape `gemm_bf16_config_for` from the on-device autotuner (recover
   the 11–15% margin on the three small-`N` shapes).
