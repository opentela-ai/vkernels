# gemm-bf16 — bf16 wmma GEMM (NVIDIA GB10, sm_121)

A roofline analysis and per-shape tuning note for the **NVIDIA CUDA port**
of the bf16 dense GEMM in `src/c/vkernels/kernels/gemm_bf16.{cpp,cu}`
(issue #29, originally AMD-MFMA on gfx942 — see [[gfx942]]): the Kimi-K3
projection shapes that today fall back to AITER's untuned
"torch solution:0". The CUDA kernel is the line-for-line algorithmic
twin of the HIP one (16×16×16 `mma_sync` in place of `__builtin_amdgcn_mfma_*`,
same two-phase tiled loop, same bounds-checked epilogue), so the two ports
are directly comparable shape-by-shape — **same algorithm, two memory
subsystems**. The CUDA path additionally runs a `cp.async` double-buffered
variant of the same loop (**1.3–1.8×** on GB10; see below) and, for warmup,
an M-grouped **cross-tile B-reuse** variant that keeps one `sB` resident
across several M-tiles (**2–34%** on GB10, largest on the small-K shapes),
while the HIP port keeps the synchronous form.

> **Measured on NVIDIA GB10 (`ds5` = `dgx-spark-05`), aarch64, compute
> 12.1 (sm_121), CUDA 13.0.88.** Peaks are *measured in-binary*, not
> datasheet arithmetic: **48 SMs, ≈252 TFLOP/s bf16** (a register-resident
> `wmma` throughput micro-kernel — the tiled GEMM itself is memory-bound
> and cannot probe the compute roof), **≈227 GB/s** (a read-only copy
> kernel), **ridge ≈1108 FLOP/byte**. The CPU reference (`gemm_bf16_cpu`,
> fp32 accumulate + single round-to-nearest-even bf16 store) is
> mathematically identical to a torch CPU bf16 matmul, so the on-device
> CUDA-vs-CPU check (max_rel ≤ 0.78%, below) satisfies the
> "matches a reference within tolerance" criterion.

## Why this port exists

`[[gfx942]]` is the only baseline the repo had. The same algorithm ported
to a consumer-class NVIDIA chip answers a question the gfx942 note poses
explicitly ("how does the same algorithm map per arch, not which is
faster"): **GB10 is a Grace-Blackwell *desktop* SoC with LPDDR memory
(~227 GB/s), whereas MI300A is a datacenter APU with HBM3 (~5300 GB/s) —
a 23× memory-bandwidth gap.** Because the tiled GEMM is HBM-bound at every
shape (`AI ≈ 2·BN ≈ 32`, well under either ridge), the port is dominated
by that gap and lets us see exactly where the algorithm stops scaling.

## Kernel (pseudocode)

```cpp
// C[M,N] = α·(A[M,K] @ B[K,N]) + β·C[M,N],  all bf16, fp32 accum
// Config: BM×BN output tile, BK=64 K-tile, (BM/16)·(BN/16)·32 threads.
// Grid: (⌈M/BM⌉, ⌈N/BN⌉)  — m_tile=blockIdx.x, n_tile=blockIdx.y.
//
// Each warp owns a 16×16 output fragment; lane = threadIdx.x & 31.
// A is read ⌈N/BN⌉ times, B is read ⌈M/BM⌉ times (no cross-tile reuse).

using namespace nvcuda::wmma;
fragment<matrix_a,    16,16,16,__nv_bfloat16,row_major> a;
fragment<matrix_b,    16,16,16,__nv_bfloat16,row_major> b;
fragment<accumulator, 16,16,16,float> c; fill_fragment(c, 0);
__shared__ uint16_t sA[BM][BK], sB[BK][BN];
for (int kt = 0; kt < (K+BK-1)/BK; ++kt) {
  // cooperative loads (uint2 = 4 bf16), M/N/K bounds-checked to 0
  for (int i = threadIdx.x; i < BM*BK/4; i += blockDim.x) { /* sA */ }
  for (int i = threadIdx.x; i < BK*BN/4; i += blockDim.x) { /* sB */ }
  __syncthreads();
  for (int mf = 0; mf < BK/16; ++mf) {            // 4 mma_sync per K-tile
    load_matrix_sync(a, &sA[warp_r*16][kt*BK+mf*16], BK);   // row major
    load_matrix_sync(b, &sB[kt*BK+mf*16][warp_c*16], BN);   // row major
    mma_sync(c, a, b, c);
  }
  __syncthreads();
}
// epilogue: store_matrix_sync into C with M/N bounds-check
```

The CUDA public path runs a double-buffered variant of the same loop:

```cpp
__shared__ uint16_t sA[2][BM][BK], sB[2][BK][BN];   // two-deep ring
issue_async(/*kt=*/0, /*buf=*/0); cp.async.commit_group();
for (int kt = 0; kt < nkt; ++kt) {
  const int buf = kt & 1;
  if (kt + 1 < nkt) { issue_async(kt+1, buf^1); cp.async.commit_group();
                      cp.async.wait_group 1; }   // kt ready, kt+1 in flight
  else                cp.async.wait_all();
  __syncthreads();
  for (mf = 0; mf < BK/16; ++mf) { /* same wmma on sA[buf], sB[buf] */ }
  __syncthreads();   // ring slot buf is free for the kt+2 issue
}
// identical bounds-checked epilogue
```

For warmup (`M > 64`) the same loop is M-grouped: each block owns `RM`
consecutive M-tiles for one N-tile and one `sB[BK][BN]` feeds all `RM`
M-panels, so each `b_frag` (shared→register) is amortised over `RM`
`mma_sync`s and global B reads drop by `RM`:

```cpp
__shared__ uint16_t sA[2][RM][BM][BK], sB[2][BK][BN];  // cp.async ring
// warp (warp_r, warp_c) keeps RM accumulator fragments, c_frag[RM]
for (int kt = 0; kt < nkt; ++kt) {
  issue_async(kt+1, buf^1); cp.async.wait_group 1; __syncthreads();
  for (mf = 0; mf < BK/16; ++mf) {
    load_matrix_sync(b, &sB[buf][mf*16][warp_c*16], BN);   // once per RK
    for (int r = 0; r < RM; ++r) {
      load_matrix_sync(a, &sA[buf][r][warp_r*16][mf*16], BK);
      mma_sync(c_frag[r], a, b, c_frag[r]);
    }
  }
  __syncthreads();
}
// epilogue: RM bounds-checked stores
```

Full source: `src/c/vkernels/kernels/gemm_bf16{.hpp,.cpp,.cu}`. The HIP
MFMA kernel (`gemm_bf16.hip`) is the line-for-line anchor: same two-phase
loop, same `(BM,BN)` grid, same bounds-checked epilogue, with each AMD
`__builtin_amdgcn_mfma_f32_16x16x16bf16_1k` replaced by the NVIDIA
`mma_sync` on a `(16,16,16)` bf16 fragment. The correctness oracle is the
*same* `gemm_bf16_cpu` (fp32 dot-product, single RNE bf16 store) shared
with the HIP port.

## What was implemented

- **CPU oracle + config selector** (`gemm_bf16.cpp`, always compiled, the
  *same file* as the HIP port — zero host-side duplication): `gemm_bf16_cpu`
  and `gemm_bf16_config_for(M,N,K,&bm,&bn,&bk,&threads)`.
- **CUDA wmma kernel** (`gemm_bf16.cu`, gated on `VKERNELS_HAS_CUDA`):
  `gemm_bf16_kernel<BM,BN>` with cooperative `uint2` loads, M/N/K
  bounds-checking, the 16×16×16 `mma_sync` K-loop, and a bounds-checked
  epilogue. Per-warp fp32 staging is in *dynamic* shared memory (one 16×16
  float per warp), with a **once-per-kernel** `cudaFuncSetAttribute` opt-in
  (a static guard) — needed for the 64×128 tile (24 KB static + 32 KB
  dynamic > the 48 KB default cap), harmless for the rest. `BK = 64` is
  fixed (every K3 `K` is a multiple of 64).
- **cp.async double-buffered kernel** (`gemm_bf16_kernel_db<BM,BN>`, the
  CUDA public path since the pipeline rung landed): identical tile mapping
  and bounds-checked epilogue, but the K-tile loads go through a two-deep
  shared ring using `cp.async.cg.shared.global` and are awaited only one
  tile ahead (`cp.async.commit_group` / `wait_group 1`), so the
  global→shared transfer of tile `kt+1` overlaps the tensor-core `wmma` of
  tile `kt`. Out-of-range 16-byte chunks use the `src-size = 0` form to
  zero-fill without reading global (the source pointer is never
  dereferenced). Requires `K % 8 == 0 && N % 8 == 0`; every K3 shape
  satisfies both, and `gemm_bf16_db_with_config` otherwise falls back to
  the synchronous kernel. Measured **1.3–1.8×** faster than the
  synchronous kernel (bit-exact output).
- **Cross-tile B-reuse kernel** (`gemm_bf16_kernel_reuse<BM,BN,RM>`, the
  CUDA warmup path): each block covers `RM` consecutive M-tiles for one
  N-tile, so a single `sB[BK][BN]` feeds `RM` M-panels. It keeps the
  cp.async double-buffered ring above, adds `RM` register accumulators per
  warp, and amortises each `b_frag` load over `RM` `mma_sync`s. Global B
  reads drop by `RM` and L1TEX/register-file pressure drops with them.
  Requires the same `K % 8 == 0 && N % 8 == 0` alignment; otherwise it
  falls through to the db kernel (and from there to the synchronous one).
- **`cuda_compat/hip/hip_fp16.h` shim** (new): a ROCm-guarded one-line
  mapping to `<cuda_fp16.h>`, so any future `.hip` port that uses `__half`
  compiles through the existing `hip_runtime.h` shim on CUDA. (Built and
  exercised on GB10; ready for the MFMA ports — issues #51, #56, etc.)
- **Four entry points**: `gemm_bf16` (shape-selected: reuse for `M > 64`,
  cp.async for serving), `gemm_bf16_with_config` (explicit-tile
  synchronous), `gemm_bf16_db_with_config` (explicit-tile cp.async),
  `gemm_bf16_reuse_with_config` (explicit-tile reuse; both benchmark only).
  The first two mirror the HIP API exactly.
- **CUDA-vs-CPU correctness harness** (`test_gemm_bf16_correct.cu`): all
  K3 shapes at `M = {8, 64}` plus `M = 8192` for the two smallest shapes,
  an unaligned public-entry case (`M=16, N=100, K=128`) that exercises the
  cp.async fallback, an explicit-tile sweep over all seven compiled
  tiles on the same awkward shape, and a cross-tile B-reuse sweep over
  `(16,64,RM4)`, `(32,64,RM2)`, `(32,64,RM4)`, `(64,64,RM2)` on
  `M=128, N=128, K=256` plus the unaligned fallback chain — tolerance
  `max_rel < 2e-2`.
- **Latency / TFLOP / GB/s benchmark + per-shape tile autotuner**
  (`bench_gemm_bf16.cu`): serving `M = {5,8,16,32,64}`, warmup `M = 8192`,
  all K3 shapes, a `(BM, BN)` sweep at every serving `M` and at warmup
  `M = 8192` — for **both** the synchronous and cp.async kernels — and a
  `(BM, BN, RM)` cross-tile-reuse sweep at `M = {5,16,64,8192}`. The bf16
  compute roof and the HBM roof are *both measured in-binary* (see Method).

## Method

- **Compute roof (measured):** `wmma_throughput_k` — each warp does
  100 000 register-resident 16×16×16 `mma_sync` accumulations (HBM traffic
  O(1)), so the kernel is purely compute-bound. Measured median ≈ **252
  TFLOP/s bf16**. The tiled GEMM itself is *memory-bound at every shape*
  (`AI ≈ 2·BN ≈ 32 ≪ 1108`), so it cannot be used to probe the compute roof
  (an earlier version that timed the GEMM on `M=8192` reported a bogus
  "peak" of 8 TFLOP/s — that was the *memory* roof, not the compute roof).
- **Memory roof (measured):** a read-only `copy_k` over 512 MiB → **≈227
  GB/s** (GB10 LPDDR, not HBM).
- **Algorithmic bytes** (minimum the answer requires): `A` once, `B` once
  across M-tiles, `C` once → `(M·K + K·N + M·N) × 2` B.
- **Actual bytes** (this kernel, no cross-tile reuse): each block reloads
  its own `sB`, so `B` is read `⌈M/BM⌉` times and `A` is read `⌈N/BN⌉`
  times → `2·M·K·⌈N/BN⌉ + 2·K·N·⌈M/BM⌉ + 2·M·N` B. **Identical to the
  HIP kernel's model** — this is what makes the cross-arch comparison fair.
- **Arithmetic intensity** `AI = 2·M·N·K / actual_bytes`. With `BN = 64`
  this is `≈ 13` at serving `(16,64)` and `≈ 31` at warmup `(64,64)`
  (MI300A's `BN = 16` serving tile gives `≈ 8`). Since `AI ≪ ridge
  (≈1108)` on GB10 (and `AI ≪ 245` on MI300A), **every shape is
  memory-bound on both chips** — the ceiling is `AI × effective_HBM`, never
  the compute roof.

## Config (`gemm_bf16_config_for`, now per-arch)

The selector is arch-gated: the CUDA branch (`VKERNELS_HAS_CUDA`) returns
the GB10 tiles below, while the HIP/host branch keeps MI300A's `(16,16)`
for serving (see [[gfx942]]). The GB10 rows are the on-device autotuner
winners for the **cp.async double-buffered** kernel (now the CUDA public
path) — the pipeline shifts the optimum away from the synchronous kernel's
`(32,64)`.

| M | BM | BN | BK | threads | regime |
|---:|---:|---:|---:|---:|---|
| ≤ 64 and `N ≤ 1024` | 16 | 16 | 64 | 32 | serving, small-N corner (`896×7168`: `(16,16)` ≈40% better than `(16,64)` at `M=64`) |
| ≤ 64 (default) | 16 | 64 | 64 | 128 | serving; within ~15% of the per-shape optimum on almost all K3 shapes, wins most |
| > 64 | 64 | 64 | 64 | 256 | warmup / prefill; the effective `(64,64)` footprint is realised as a 4-way M-grouped `(16,64)` reuse kernel (`BM=16, RM=4`), the measured winner on all eleven K3 shapes at `M=8192` |

`(16,64)` is now the serving default: the small `BM` keeps the block count
high while `BN=64` gives the async copies a full row to work on. It is
1.4–1.8× faster than the previous `(32,64)` rows *and* 3–4× faster than the
pre-arch-config `(16,16)` (e.g. QKV `6288×7168` at `M=64`: 2248 → 986 →
`~547 µs`). With the pipeline in place, warmup uses the M-grouped
`(16,64,RM4)` reuse kernel, which reports the same `(64,64)` output
footprint (and therefore the same no-reuse byte model) but amortises the
`b_frag` register load over 4 M-fragments. It is the measured winner on
every `M=8192` K3 shape: 2–6% faster than the flat `(64,64)` cp.async tile
on the large-K shapes and **26–52%** faster on the small-K ones
(`K = 128…1536`, where B reuse dominates) — QKV `6288×7168`: 55400 →
53588 µs; `7168×1536`: 13403 → 8954 µs; `7168×768`: 6767 → 4456 µs.

The explicit-tile dispatcher (`cuda::gemm_bf16_with_config`) also compiles
`(16,64), (16,128), (32,64), (32,128), (64,128)` for the autotuner. The
reuse dispatcher (`cuda::gemm_bf16_reuse_with_config`) compiles
`(16,64,RM4)`, `(32,64,RM2)`, `(32,64,RM4)`, `(64,64,RM2)`.

kernel and ~13.3 TFLOP/s for the flat cp.async tile). The cp.async pipeline
lifted every shape: QKV `6288×7168` is **82288 → 55400 µs (1.49×)**. The
cross-tile B-reuse rung then lifted the small-K shapes again — `7168×1536`
13403 → 8954 µs, `7168×768` 6767 → 4456 µs, `2304×1536` 4309 → 2835 µs,
`3072×512` 1953 → 1312 µs, `1536×128` 262 → 210 µs — and gave a smaller
2–6% on the large-K ones. The win is **not** a DRAM-traffic effect (ncu
showed GB10 DRAM at only 48–58% of its LPDDR roof, and reuse does not
change the first-touch B bytes); it is the same L1TEX/register-pressure
effect the flat sweep attributed to `(32,64)`: one `b_frag` register load
now feeds four `mma_sync`s instead of one, and the per-warp accumulator
count is what sets the shared→register traffic. That is why reuse helps
most exactly where `B` is re-read most relative to `A` — small `K`,
large `N`. The earlier claim that `(64,64)`'s extra B reuse was "free"
once pipelined was true only of *DRAM* reuse; the L1TEX reuse still cost,
and the M-grouped form recovers it.

MI300A is flat at ~73–78 TFLOP/s ≈ `31 × 2400`, pinned to its *effective*
HBM roof (45% of its 5300 peak). At warmup the two chips still run the
**same memory-bound kernel at their respective effective-HBM ceilings**,
so the **~4–5.6× TFLOP/s gap is now mostly the bandwidth gap** (down from
8–9× for the synchronous kernel), with a smaller residual latency term on
the 48-SM SoC. The GB10 reuse gain also means the *algorithmic* `AI`
ceiling is no longer purely `2·BN`: on the small-K shapes the kernel is
now closer to the reuse-limited intensity than the flat tile was.

## ncu counter evidence — why neither chip is actually DRAM-bound

The roofline above models `AI` from a no-reuse byte count — but `ncu` shows
the *real* DRAM traffic is far lower, because L2 absorbs most re-reads.
Profiled on GB10 for QKV `6288×7168` at `M = 8192` (one launch, `ncu`
instrumentation; wall times are inflated ~8% by the profiler):

| tile | time (ms) | SM % | L1TEX % | L2 % | L2 read (GB) | L2 read-miss = DRAM read (GB) | DRAM GB/s | warps active % |
|:---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 32×64 | 90.4 | 47.3 | 78.7 | 22.2 | 34.7 | 11.73 | **132** | 66.5 |
| 64×64 | 108.8 | 32.9 | 62.0 | 11.9 | 23.2 | 11.93 | **110** | 66.5 |

(`lts__t_sectors_srcunit_tex_op_read_lookup_miss × 32 B`; writes add
~55 MB. The L2 request volume matches the no-reuse model byte-for-byte —
34.7 GB and 23.2 GB — so the model is right about *SM-side* traffic.)

Three things fall out:

1. **DRAM is at 48–58% of the measured 227 GB/s LPDDR roof**, not 100%.
   L2 hit rate is 48% (64×64) to 66% (32×64), and — crucially — *both*
   tiles miss to DRAM by almost the same ~11.8 GB, because the miss traffic
   is the first touch of the `K×N` B panel, not the modeled re-read
   count. **Cross-tile B reuse cannot help GB10 much:** the DRAM wall is
   not what is stopping this kernel, and a persistent/multi-M-tile
   schedule would shrink the grid that the `(32,64)` result shows matters.
2. **No unit is saturated.** SM 33–47%, L1TEX 62–79%, L2 12–22%, DRAM
   48–58%. The kernel is **latency / serialisation bound**: the two-phase
   `load → __syncthreads → wmma → __syncthreads` leaves the LSU idle while
   the tensor cores run and vice-versa. That is the `cp.async` double-buffer
   rung, not the reuse rung.
3. **`(32,64)` beat `(64,64)` on SM throughput** (47% vs 33%) at equal
   occupancy (66.5% warps active both), which is why the *synchronous*
   selector picked it despite moving 50% more bytes through L2. That
   ordering flips once the loads are pipelined (see below).

So the GB10 ladder was reordered versus MI300A: **cp.async double-buffer
first** (overlap the two phases on a DRAM-bound-free kernel), then
register blocking to cut L1TEX traffic; cross-tile B reuse is the MI300A
lever and should not be ported blindly. The cp.async rung was then
implemented and **confirmed the diagnosis**: the double-buffered kernel is
1.3–1.8× faster on every measured shape and reorders the tiles again —
serving `(16,64)`, warmup `(64,64)` — because it overlaps exactly the
`load` / `wmma` phases that were serialising. DRAM is still only ~50–60%
of the LPDDR roof afterwards, so there is more latency to hide, but the
first rung paid off.

**Reconciliation (reuse rung).** The prediction above that "cross-tile B
reuse cannot help GB10 much" was right about *DRAM* and wrong about the
rest of the machine. The M-grouped reuse kernel changes neither the
first-touch `K×N` B bytes (still ~11.8 GB) nor the DRAM roof utilisation,
yet it is 26–52% faster on the small-K shapes and 2–6% on the large-K ones.
The mechanism is the L1TEX at 62–79%: `b_frag` is a shared→register load,
and the flat tile pays it once per `mma_sync`; the `RM`-grouped tile pays
it once per `RM` `mma_sync`s. So the reuse rung that is a *DRAM* lever on
MI300A is an *L1TEX/register-blocking* lever on GB10 — the same rung, a
different bottleneck, which is exactly why it had to be measured rather
than inferred from the DRAM counters alone. The flat `(64,64)` tile's "free
B reuse" after pipelining was free only in DRAM terms.

## Autotuner — full tile matrix (us(med), serving M = {5,8,16,32,64})

Lower is better. `best` is the winning tile for that shape. The bench now
sweeps **both** kernels; below is the cp.async kernel (the public path).
**Key GB10 finding with the pipeline: `(16,64)` wins most serving shapes
while `(16,16)` takes the small-N corner** — the opposite of the
synchronous kernel, where `(32,64)` won ~90% of shapes. The base-kernel and

The old synchronous `(16,16)` default was therefore **4.1× slower than the
current `(16,64)` cp.async path on the `M = 64, N = 6288, K = 7168` QKV
shape** (2248 vs 547 µs) and 3–4× slower across the sweep. This is now
fixed: `gemm_bf16_config_for` is per-arch and returns the rows in Config
above for GB10, retiring this note's original "documented next step".

shipped warmup kernel; `32×64/RM4` (effective 128×64) is the best
alternative on the large-K shapes, but its ~2% edge is within run-to-run

## Correctness

`test_gemm_bf16_correct_cuda` was run on GB10 (sm_121). **All checks passed
(0 failures)**, byte-for-byte the same harness as the HIP one:

- All 11 K3 shapes at `M = {8, 64}`: `max_abs ≤ 0.25`, `max_rel ≤ 0.78%`
  (well under the `2e-2` tolerance).
- Warmup `M = 8192` for `(1536, 128)`, `(3072, 512)`, and `(64, 7168)`
  (now on the `(16,64,RM4)` reuse warmup path): `max_rel ≤ 0.78%`.
- The **cp.async fallback**: `(M=16, N=100, K=128)` has `N % 8 ≠ 0`, so
  `gemm_bf16_db_with_config` falls back to the synchronous kernel;
  `max_abs = 0`, `max_rel = 0`. Every K3 shape is 8/64-aligned, so this is
  the only coverage of the fallback.
- **Cross-tile B-reuse sweep** on `M=128, N=128, K=256` (spans >1 M-tile
  for every config): `(16,64,RM4)`, `(32,64,RM2)`, `(32,64,RM4)`, and
  `(64,64,RM2)` all give `max_abs = 0.0010`, `max_rel ≤ 0.10%`. The
  unaligned `(16,100,128)` case exercises the reuse → db → synchronous
  fallback chain (`max_rel = 0`).
- Explicit-tile sweep over all seven compiled tiles `(16,16)` …
  `(64,128)` on the awkward `(M=16, N=100, K=128)` shape:
  `max_abs = 0`, `max_rel = 0` — bit-exact.

The reference is the *same* `gemm_bf16_cpu` (fp32 accum, single RNE bf16
store) used by the HIP port — i.e. the CUDA kernel matches the same
oracle the HIP kernel matches, at the same tolerance. The cp.async kernel
was additionally checked **bit-exact against the synchronous kernel** with
a scratch driver on the QKV shape at `M ∈ {64, 8192}` and on `M=8192,
N=1536, K=128` (same wmma accumulation order).

## Caveats and limitations

1. **Same algorithm, so the same memory-bound ceiling as [[gfx942]]** —
   with a GB10-specific wrinkle. The flat tile has no cross-tile B reuse
   (`AI ≈ 2·BN`); the warmup path now uses `RM`-M-grouped reuse, which
   leaves the no-reuse *byte model* unchanged (the grid still covers
   `BM·RM` rows) but cuts the L1TEX `b_frag` traffic by `RM`. ncu showed
   the *synchronous* kernel was in fact **latency/serialisation bound**,
   not DRAM bound (DRAM at 48–58% of the LPDDR roof, no unit above ~79%);
   the cp.async double-buffer (**1.3–1.8×**) removed most of that, and the
   reuse rung added **2–52%** on top by cutting the L1TEX/register traffic
   that the flat tile still paid. Cross-tile reuse remains the
   highest-leverage *DRAM* algorithm step for MI300A; on GB10 it landed as
   an L1TEX lever instead, and only for warmup — serving is already at the
   DRAM roof.
2. **GB10 is the wrong chip for this workload.** A desktop SoC with 227
   GB/s LPDDR is 23× below MI300A's 5300 GB/s HBM3, and this kernel is
   HBM-bound everywhere, so GB10 runs 1.8–9.4× slower across the serving
   sweep. The port's value is **arch mapping**, not throughput — a
   datacenter NVIDIA peer (A100/H100, HBM2e/HBM3) is the fair fight and
   remains future work.
3. ~~**The default tile is wrong for GB10.**~~ **Retired (per-arch config
   landed, then re-tuned for cp.async).** `gemm_bf16_config_for` is no
   longer shared: the CUDA branch returns GB10's measured `(16,64)` /
   `(64,64)` tiles and the HIP/host branch keeps MI300A's `(16,16)`. The
   GB10 serving curve is now flat (~442–547 µs across `M = 5…64`, versus
   636 → 2248 µs before the arch config and 986 µs at `M=64` after it),
   and the `M=64` QKV shape is **4.1×** faster than the pre-fix default.
4. **GB10/CUDA-13 `cudaEventElapsedTime` glitch.** Batches of ≳160 rapid
   re-launches (the adaptive loop's larger batches, `max_iters=500`)
   intermittently return `ms == 0` on GB10, producing `0 µs / inf
   TFLOP/s` rows. The bench caps `bench_us` at `max_iters=80` (the same
   cap the autotuner already used, where it is unaffected), which keeps
   per-launch event medians clean and reproducible (verified across 3
   runs, 0 spurious rows). A zero-drop + chrono fallback remain in
   `bench_us` as a backstop for any residual glitch.
5. **Tiny kernels are below the event timer** (~0.5 µs). The smallest
   shapes `(3072, 512)` and `(1536, 128)` at low `M` are 8–37 µs — timed
   reliably at `max_iters=80` (unlike the sub-µs regime on MI300A).

## Journal

**What was done.** Ported the bf16 K16-MFMA dense GEMM of [[gfx942]] to
NVIDIA CUDA wmma for the Kimi-K3 projection shapes — `gemm_bf16.cu`
(gated on `VKERNELS_HAS_CUDA`, reusing the shared `gemm_bf16.cpp`
oracle/selector), a CUDA-vs-CPU correctness harness (`test_gemm_bf16.cu`),
a latency/TFLOP/GB/s benchmark with a per-shape tile autotuner and
*both* roofs measured in-binary (`bench_gemm_bf16.cu`), and a
`cuda_compat/hip/hip_fp16.h` shim for future `.hip` ports. The whole CUDA
backend builds at `-arch=sm_121` and ctest is 47/47.

**On-device validation (ds5, GB10).** Built with CUDA 13.0.88 at
`-arch=sm_121`. Correctness harness passed completely (0 failures,
`max_rel ≤ 0.78%`, explicit-tile sweep bit-exact). The benchmark measured
the serving sweep, the warmup sweep, and the full `7-tile × 11-shape ×
5-M` autotuner matrix, then this roofline note.

**Challenges.**
1. *Bogus "compute peak".* The first roofline used the GEMM itself as the
   compute probe; it is memory-bound (`AI ≈ 32`) and reported 8 TFLOP/s —
   the *memory* roof. Replaced with a register-resident `wmma_throughput_k`
   (HBM traffic O(1)) → a real 252 TFLOP/s bf16 compute roof.
2. *`cudaEventElapsedTime` returns 0 on GB10.* Rapid re-launch batches
   (≥160) intermittently yield `ms == 0` → `inf TFLOP/s` rows, on shapes
   that ran fine standalone (confirmed: the kernel output is correct for
   all "failing" shapes). Root cause is the batch size, not the kernel:
   capping `bench_us` at `max_iters=80` (matching the unaffected
   autotuner) eliminates it; a zero-drop + chrono backstop remains.
3. *Shared-memory cap.* The 64×128 tile's static `sA/sB` (24 KB) + dynamic
   staging (32 KB) exceed the 48 KB default per-block cap; moved the
   staging to dynamic shared with a once-per-kernel
   `cudaFuncSetAttribute` opt-in (static guard), and called it once rather
   than per-launch (the per-launch call perturbed the event clock).

**Follow-up (warmup tile sweep).** Added a second tile sweep at warmup
`M = 8192` to `bench_gemm_bf16.cu` (the serving autotuner only covered
`M ≤ 64`). It found `(32,64)` ~1.2× faster than `(64,64)` on every large-K
shape and `(64,64)` still best on small-K — i.e. on GB10 the binding
constraint is block count / latency hiding, not B reuse. Folded into
`gemm_bf16_config_for` (`M > 64, K > 2048` → `(32,64)`), added a `K > 2048`
warmup correctness case (`M=8192, N=64, K=7168`), and re-verified: CUDA
unit 7/7, correctness 0 failures, host ctest 39/39. QKV `M=8192`:
95458 → 82521 µs.

**ncu counter readout.** Profiled the QKV `M=8192` launch with
`/usr/local/cuda/bin/ncu` (full CUDA ncu is present on this GB10 host).
DRAM counters are `n/a` on the SoC, but `lts__t_sectors_*_lookup_miss`
gives L2→DRAM traffic: 11.7–11.9 GB read for *both* tiles, ~110–132 GB/s
= 48–58% of the 227 GB/s LPDDR roof, with no unit saturated (SM 33–47%,
L1TEX 62–79%, L2 12–22%). This **reorders the ladder for GB10**: the
kernel is latency/serialisation bound, not DRAM bound, so `cp.async`
double-buffering is the first rung and cross-tile B reuse is not. Written
up in the gb10 note; the profiling driver was scratch (`/tmp/prof_gemm`),
not committed.

**cp.async double-buffer landed.** Implemented `gemm_bf16_kernel_db<BM,BN>`
(two-deep shared ring, `cp.async.cg` 16-byte chunks with `src-size=0`
zero-fill for out-of-range chunks, `commit_group` / `wait_group 1` so tile
`kt+1` loads while tile `kt` computes) and wired `gemm_bf16` to use it,
with a synchronous fallback for shapes where `N % 8 ≠ 0`. Extended the bench
autotuner to sweep both kernels and re-ran the full `7-tile × 11-shape ×
5-M` serving matrix and the `M=8192` warmup matrix on GB10. Results:
bit-exact vs the synchronous kernel, **1.3–1.8×** faster on every shape,
and the tile optimum moved to serving `(16,64)` / warmup `(64,64)` — the
synchronous-kernel `(32,64)` warmup was reverted. QKV 6288×7168: `M=64`
986 → **547 µs**, `M=8192` 82288 → **55400 µs**. Folded into
`gemm_bf16_config_for`, added the unaligned fallback test, and re-verified:
CUDA unit 7/7, correctness 0 failures (including the new fallback case),
host ctest 39/39. The ncu-informed prediction (latency-bound, not
DRAM-bound) held.

**Cross-tile B-reuse landed (warmup).** Implemented
`gemm_bf16_kernel_reuse<BM,BN,RM>` (one `sB` resident across `RM` M-tiles,
cp.async ring, `RM` register accumulators per warp) and an
`gemm_bf16_reuse_with_config` benchmark hook, wired `gemm_bf16` to use the
`(16,64,RM4)` form for `M > 64`, and extended the correctness harness with a
reuse sweep plus the reuse→db→sync fallback chain. Added a `(BM,BN,RM)`
sweep to the bench. Results on GB10 (public path): 2–6% faster than the flat
`(64,64)` cp.async tile on the large-K shapes and **26–52%** faster on the
small-K ones — QKV `6288×7168` `M=8192` 55400 → **53588 µs**,
`7168×1536` 13403 → **8954 µs**, `7168×768` 6767 → **4456 µs**,
`2304×1536` 4309 → **2835 µs**, `3072×512` 1953 → **1312 µs**,
`1536×128` 262 → **210 µs**. At serving `M ≤ 64` the reuse path is
uniformly *slower* (the serving kernel is already at the DRAM roof, so
reuse has no traffic to save and the flat tile's extra blocks win), so it
is gated on `M > 64`. The mechanism is L1TEX/register blocking, not DRAM —
ncu's DRAM counters predicted "reuse cannot help", and they were right
about DRAM and wrong about the SM. Verified: CUDA unit 7/7, correctness 0
failures (original + reuse sweep + fallback chain), host ctest 39/39.
