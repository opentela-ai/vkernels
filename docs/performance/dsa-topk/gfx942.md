# dsa-topk — paged-MQA gated top-k logits (AMD gfx942, MI300A)

A roofline + occupancy characterization of the DSA indexer kernel in
`src/c/vkernels/kernels/dsa.{cpp,hip}` (issue #51) — the **first stage**
that feeds `dsa_sparse_fwd`: each query scores its paged KV tiles and the
integrator's top-k then selects the blocks to attend over.

$$\text{out}[b, t] = k\_scale[\,page[b,i],\,j\,] \cdot \sum_h \Big(\max\!\big(0,\, \textstyle\sum_d Q[b,h,d]\,K[page[b,i],j,d]\big) \cdot gate[b,h]\Big)$$

where `t = i*block + j`, `t < seq_lens[b]` (else left unwritten). The
host reference (`dsa_topk_logits_cpu`) is fp32 end-to-end. The device has
**two variants**, dispatched by `dsa_topk_logits_fits_lds` /
`dsa_topk_logits_fits_lds_fp8q` against gfx942's 64 KB non-optin dynamic-LDS
cap (whose opt-in ceiling EQUALS the non-optin cap — there is NO
`hipFuncSetAttribute` opt-in past 64 KB, verified on this node; see the KB
note `mi300a-dynamic-lds-no-optin`):

  * **fp32-Q** — the fast path. Q dequanted once into shared and reused
    across all H heads. Covers the GLM-5.3 `index_n_heads` (H=32,
    49,536 B < cap); the verified, byte-for-byte baseline below.
  * **fp8-Q** — the fallback for H=64..246. Q staged as **raw fp8 e4m3fnuz**
    (1 B/elem), dequanted on the fly in the dot loop with the SAME
    `fp8e4m3fnuz_to_f32` helper. The dequanted Q values, the fp32
    accumulator and the written output are **bit-identical** to the fp32-Q
    kernel, so the cross-check below (max_rel < 1e-3) carries over
    unchanged.

Measured on a CSCS beverin MI300A compute node (`srun --partition=mi300 -N1
-G1`, ROCm 6.3.0, gfx942:sramecc+:xnack-). Full raw log:
[`beverin-dsa-topk-bench.log`](beverin-dsa-topk-bench.log). Reproduce with
`meta/scripts/run_dsa_topk_bench_mi300.sh` (builds `test_dsa_topk_correct`
+ `dsa_topk_logits_bench` and runs both).

## Decode latency — GLM-5.3 indexer (the headline)

`bs=1, H=32, D=128, B=64, split=1` (the no-tuning baseline the integrator
gets by default), sweeping `max_table_len`:

| max_seq_len | mt | us(min) | us(med) |  GB/s |   AI |
|------------:|---:|--------:|--------:|------:|-----:|
|         512 |  8 |   2700  |   2703  |  0.03 | 57.2 |
|        1024 | 16 |   5376  |   5385  |  0.05 | 58.9 |
|        2048 | 32 |  10729  |  10745  |  0.07 | 59.8 |
|        4096 | 64 |  21438  |  21470  |  0.09 | 60.2 |

Latency is **linear in `max_seq_len`** (~5.25 µs/token): the grid is one
wavefront that loops over the page range sequentially. This is the "it
returns at all" baseline — the tilelang path the kernel replaces hangs at
`H ∈ {32, 64}`; this kernel is verified correct and returns in single-digit
to tens of milliseconds at decode context lengths.

## H=64 decode latency — the fp8-Q fallback (2× indexer)

The GLM-5.3 2× indexer (`H=64, D=128, B=64` stages 66,048 B as fp32-Q —
OVER the 64 KB cap, for which gfx942 has **no opt-in**; see above) runs the
fp8-Q kernel, which stages Q raw (8 KB) and dequants on the fly. Same
sweep as the headline:

| max_seq_len | mt | us(min) | us(med) |  GB/s |    AI |
|------------:|---:|--------:|--------:|------:|------:|
|         512 |  8 |   8212  |   8221  |  0.0  | 108.2 |
|        1024 | 16 |  16411  |  16419  |  0.0  | 114.4 |
|        4096 | 64 |  65590  |  65628  |  0.0  | 119.6 |

Latency is again linear in `max_seq_len` (~16.0 µs/token vs 5.24 µs/token
for H=32 — a consistent **~3.0×** per-token cost): 2× more heads (2× FMA
work per token) **and** the fp8-Q kernel re-dequants each Q element inside
the dot loop rather than once at shared load. The higher AI (108-120 vs
57-60 FLOP/byte) reflects the doubled H against the same K bytes, still
well below MI300A's ~247 ridge — i.e. the fp8-Q path trades LDS (saved:
`H*D*3` = 24 KB at H=64) for ALU (re-dequant), keeping the kernel
**occupancy-bound on the same one-wavefront grid** as H=32. `split_kv`
applies to the fp8-Q path identically (one page per split distributes the
serial page loop across CUs).

## The binding constraint is OCCUPANCY, not HBM

The roofline AI (~57-60 FLOP/byte) sits well below MI300A's ridge (~247
FLOP/byte), which on paper classifies the kernel as memory-bound. **But the
working set for these shapes is 68-560 KB — L2-resident after the 5-launch
warmup** — so the reported "GB/s" is over the L2-resident working set, NOT
a meaningful fraction of the 5300 GB/s HBM3 roof (note the 0.03-0.09 GB/s
column, i.e. ≤0.01% of HBM). The real limiter at decode is that the grid is
**one wavefront on one of MI300A's 228 CUs**; a single wavefront's serial
page loop + fp8→fp32 dequant + D=128 dot-product dependency chain bounds
the latency, not any bandwidth.

### split_kv — the critical perf knob (near-linear speedup)

`split_kv` slices the page range `[0, ceildiv(max_seq_len, B))` across more
blocks per batch (perf-only — the grouped logit is grouping-independent,
verified by `test_dsa_topk_correct` case `split=2`). At the largest decode
(`max_seq_len=4096`, one wavefront takes 21.5 ms), sweeping `split_kv` to
its maximum (`ceildiv(4096, 64) = 64` — one page per split):

| split_kv | us(min) | us(med) | GB/s | speedup |
|---------:|--------:|--------:|-----:|--------:|
|        1 |  21496  |  21523  | 0.03 |   1.0×  |
|        2 |  10761  |  10773  | 0.06 |   2.0×  |
|        4 |   5397  |   5401  | 0.13 |   4.0×  |
|        8 |   2707  |   2711  | 0.26 |   7.9×  |
|       16 |   1364  |   1366  | 0.52 |  15.8×  |
|       32 |    692  |    694  | 1.04 |  31.0×  |
|       64 |    356  |    359  | 2.08 |  59.9×  |

**Near-linear speedup to 59.9× at split=64** (the max — one page per
split, 64 of the 228 CUs used). The integrator should set

```text
split_kv = max(1, min( ceildiv(max_seq_len, block), 228 / batch_size ))
```

with `NUM_CU = 228` (MI300A / gfx942, `hipDeviceProp_t.multiProcessorCount`,
verified on this node — the `hip_capi.hpp` ABI docstring previously
stated the cap as 256). Rather than recompute it, the integrator calls the
host helper `dsa_topk_logits_split_for(batch_size, max_seq_len, block)`
(exposed through the C ABI `vk_dsa_topk_logits_split_for` and the Python
`vkernels.kernels.dsa_topk_logits_split_for`); for the headline shape it
returns 64 and the 4096-token decode drops from **21.5 ms → 0.36 ms**.

### Batch scaling is free parallelism

At `mt=8` (max_seq_len=512), `bs` scales the grid directly (one block per
batch), so latency is essentially flat as `bs` grows until the grid

## The bf16-MFMA variant (the mk2 record issue #81 must beat)

The mk2 run
([`beverin-dsa-topk-mk2-bench.log`](beverin-dsa-topk-mk2-bench.log); ROCm
6.3.0, 228 CUs, Matrix-Core 1307 TFLOP/s bf16) added
`dsa_topk_logits_kernel_mfma`: Q staged transposed bf16 ONCE per block +
one bf16 K-tile (fp8 fullscreen converted at fill), each page's [H, B] dot
matrix carried as verified `__builtin_amdgcn_mfma_f32_16x16x16bf16_1k`
fragments, ReLU + gated H-sum + per-token k_scale in fp32. `auto`
dispatches it FIRST (smallest footprint + Matrix Core).

Oracle gate: all 12 shapes PASS (max_rel <= 1.89e-4 vs the 1e-3 gate,
including the H=64/128 fp8-Q-fallback rows, the split_kv row, and the
explicit v=fp32/fp8q/mfma rows).

The MFMA kernel stops scaling at split=64: 190 us there, 893 us unsplit.
The binding constraint is NO LONGER the Matrix Core (its utilization is
far below the 1307 TFLOP/s roof) but the serial page loop inside each
block: 2 K-tiles per page, TWO `__syncthreads` per K-tile between the
cooperative fp8->bf16 convert and the MFMAs, and no prefetch -- every
L2-resident load lands on the critical path of the one-wavefront grid.
Batch scaling under MFMA stays free parallelism (bs 1..64 flattish at
262-272 us, msl=512), preserving the free-to-~228 story.


`bs` 1 → 64 (64× more work) costs **0.6% more latency** — i.e. ~64× more
queries/second at fixed latency, up to the ~228-CU ceiling after which the
grid starts serialising across waves.

## What the follow-on closes

The kernel is a scalar GEMV baseline (one lane per KV token, sequential
H-sum, K staged once per page in fp32 and reused across all H heads — no
MFMA, no tiled-key prefetch). The `dsa.hpp` docstring previously called out
a `hipFuncSetAttribute` opt-in for >64 KB LDS as follow-on #1; **that
opt-in does not exist on gfx942** (the opt-in ceiling EQUALS the non-optin
cap, 65,536 B — verified on this node; see the KB note
`mi300a-dynamic-lds-no-optin`). It is instead closed **algorithmically**:
the fp8-Q variant (`dsa_topk_logits_kernel_fp8q`, dispatched by
`dsa_topk_logits_fits_lds_fp8q`) drops Q to raw fp8 and dequants on the
fly, covering H up to 246 at D=128, B=64 (49,920 B at H=128) —
**bit-identical output** to the fp32-Q kernel, verified above.

The remaining follow-on is the one the perf numbers point at:

* **Tiled-key / MFMA-fp8 prefetch** — raises occupancy (more work per
  wavefront, fewer serial page loops) AND moves the kernel toward the
  Matrix-Core compute roof, attacking the single binding constraint
  (one wavefront on one of 228 CUs) shared by BOTH variants.

### issue #81: fp8 K-tile prefetch ring — implemented, bit-identical, NOT a perf win

The follow-on above WAS implemented (branch `issue-81-dsa-topk-tiled-keys2`):
the mfma kernel's page range became ONE flat K-tile sequence (`tilesPerPg =
D/kBK`), double-buffered as a raw-fp8 ring `sK8[2][B][kBK]` — tile `gt`
computes from slot `gt&1` while tile `gt+1` is byte-copied into slot
`(gt+1)&1` behind ONE `__syncthreads` per tile (was two), the page table is
walked per tile so the prefetch crosses page boundaries, and the per-token
scales live in a page-parity `sKscale[2][B]` slot. Footprint:
`D*H*2 + 2*B*kBK + (H + 2B)*4` — 17,024 B at H=32 (the K bytes are
footprint-neutral: each 2-byte bf16 K became 1-byte fp8 x 2 slots; +256 B is
the second scale slot).

**Correctness (run 640245, MI300A): all 15 oracle rows PASS with the SAME
max_rel values as the pre-prefetch kernel** (0.000024 / 0.000189 / 0.000057
/ ... vs the 1e-3 gate) — the ring's per-lane fp8 -> f32 -> bf16 conversion
feeds the MFMAs the same bit patterns the fill-side convert produced, so the
outputs are bit-identical and top-k ordering is unchanged. Raw log:
`meta/benchmarks/artifacts/issue-81/run-640245-first-full.out`.

**Performance — same-node A/B** (both binaries back-to-back on one MI300A
node; the untouched fp32/fp8q variant rows measured identically in every run
on every node, so the deltas are the code, not the machine):

| shape (bs H msl, split) | prefetch ring | main (4c58c58) | delta |
|---|---|---|---|
| b=1 H=32 msl=4096, unsplit | 960.4 / 968.7 us | 897.9 / 899.7 us | **+7% slower** |
| b=1 H=64 msl=4096, unsplit | 1279.9 / 1302.8 us | 1219.8 / 1231.4 us | +5% slower |
| b=1 H=32 msl=512 | 271.9 / 274.8 us | 265.3 / 266.9 us | +3% slower |
| b=2..64 H=32 msl=512 | 272–281 us | 267–276 us | +2–5% slower |
| b=1 H=32 msl=4096, split=64 | 195.0 / 197.8 us | 194.0 / 195.3 us | parity |

A second attempt — register-staging the fill's copy (every kTh-strided load
issued before its stores, run 640265) — measured WORSE (unsplit 1159.7 us,
+29% vs main; mfma variant row 298.9 vs 267.7 us; raw log
`meta/benchmarks/artifacts/issue-81/run-640265-staged-negative.out`) and was
reverted: the compiler already pipelines the un-staged loop, and the
staging's extra ALU + register pressure cost more than it saved.

**Verdict: the ring does not beat the numbers above.** The mfma kernel's
per-tile chain is not prefetch-latency-bound — the pre-prefetch loop's two
barriers per tile were already cheap against the wavefront's MFMAs — while
the ring pays two costs the baseline does not: the per-lane fp8 -> bf16
dequant sits on the fragment path instead of a block-wide convert in the
fill, and the fill writes byte-granular LDS (half the bandwidth of the
baseline's bf16 stores). What the ring did deliver: bit-identical output,
one barrier per tile instead of two, and the same footprint that fits every
admitted width. NOTE: the A/B run's raw .out was inadvertently deleted from
the scratch after capture; the per-row numbers above are the record (they
cross-check against the `run-640245-first-full.out` log, whose shapes
overlap).

Until an owner decision lands, `v=auto` still dispatches mfma only when
`dsa_topk_logits_fits_lds_mfma` passes, so reverting the kernel to the
pre-prefetch version (main@4c58c58) touches only
`dsa_topk_logits_kernel_mfma` in `dsa.hip`.

Until then, `split_kv` is the lever the integrator has — now exposed as a
single-source-of-truth host helper, `dsa_topk_logits_split_for` (C ABI
`vk_dsa_topk_logits_split_for`, Python `vkernels.kernels.dsa_topk_logits_split_for`),
so the integrator no longer hand-computes the (previously mis-stated)
`NUM_CU` formula. The numbers above are the baseline to beat.
